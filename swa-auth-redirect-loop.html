Custom Auth Provider Redirect Loop After Deployment

Custom Auth AAD B2C 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

Authentication works fine in local development (using the SWA CLI emulator) but loops endlessly between the login provider and the app once deployed — the browser bounces from /.auth/login/aad to the identity provider and back, never landing on an authenticated page, sometimes ending in a generic error page instead.

02Environment

  • Azure Static Web Apps with a custom authentication provider (Azure AD B2C or a custom OpenID Connect provider)
  • Works correctly with the SWA CLI locally, fails only after deployment to the live environment
  • Provider configured via staticwebapp.config.json and app settings for client ID/secret

03Diagnosis

Because this works locally, the cause is almost always an environment-specific configuration gap rather than a code issue. Check in this order:

  • Redirect URI registered with the identity provider. The provider's app registration needs the exact production callback URL (e.g. https://<your-app>.azurestaticapps.net/.auth/login/aad/callback) — the local emulator's URL won't match, so this is easy to miss when moving from dev to production.
  • Provider secret configured as an application setting in the SWA resource itself (not just referenced in staticwebapp.config.json) — client secrets go in Configuration, not the config file, and a missing one causes the provider handshake to fail silently before redirecting back with an error.
  • Custom domain mismatches. If the SWA is served through a custom domain, the redirect URI registered with the provider must match the domain actually being used, not the default *.azurestaticapps.net hostname — a mismatch here causes exactly this kind of loop.
Common misdiagnosis: because the browser cycles through what looks like a normal login flow before failing, it's easy to assume the issue is with the identity provider or the user's account. In practice, if the flow never lands on an authenticated page for any user, it's almost certainly a redirect URI or secret configuration gap on your side.

04Root Cause

OpenID Connect and OAuth flows are strict about redirect URI matching as a security measure — the identity provider will refuse to complete the handshake (or silently redirect back to login) if the callback URL presented doesn't exactly match what's registered. Because local development uses a different host than production, a configuration that "works" locally can be incomplete for production without that gap being obvious until deployment.

05Fix

  • Register the exact production redirect URI with the identity provider's app registration, including the correct scheme, host, and callback path.
  • Set provider secrets in Static Web Apps Configuration (Settings → Configuration), not just referenced by name in staticwebapp.config.json — the config file defines which setting name to use, but the actual secret value has to exist in the app's configuration.
  • If using a custom domain, register that domain's callback URL with the provider as well, and confirm staticwebapp.config.json's auth configuration doesn't hardcode the default azurestaticapps.net hostname anywhere.
  • Test with a fresh browser session (or incognito) after each change — cached auth cookies can make a fixed configuration appear to still be looping.
Prevention tip: keep a checklist of environment-specific values (redirect URIs, secrets, custom domain registrations) that must be set per environment, and verify it explicitly as part of your deployment process rather than assuming local success generalizes to production.
