Capacity Planning for Container Apps: How Replicas Actually Consume Resources

Intermediate Consumption Plan 7 min read

Capacity planning for Container Apps confuses people because the mental model is different from a single VM or a fixed App Service Plan — resources are requested per-container and multiplied across replicas, and getting this wrong shows up either as throttling under load or as a surprising bill.

Before you start
  • A Container App you're planning to size, with a rough idea of expected traffic

  1. Understand the per-replica resource request

    Each container in a Container App requests a specific CPU (in vCPU cores, e.g. 0.5) and memory (in GiB, e.g. 1Gi) allocation. This is a per-replica request, not a total budget for the app — every replica gets this full allocation.

    Reasoning
    1 replica  × 0.5 vCPU, 1Gi  = 0.5 vCPU, 1Gi total
5 replicas × 0.5 vCPU, 1Gi  = 2.5 vCPU, 5Gi total

  2. Account for the min/max replica range, not just a single number

    Your minimum replica count sets your baseline steady-state consumption (and cost, if above zero), while your maximum sets your ceiling under load. Size both deliberately — a minimum of 0 (scale-to-zero) minimizes idle cost but reintroduces cold start; a minimum of 1+ avoids cold start but means you're always paying for at least that many replicas' worth of resources.

  3. Multi-container apps multiply further

    If your Container App runs multiple containers per replica (for example, your app container plus a sidecar), each container's resource request adds to the per-replica total — and that combined total is what gets multiplied by replica count.

  4. Match your scale rule threshold to realistic per-replica capacity

    If using HTTP concurrency-based scaling, the threshold should reflect how many concurrent requests a single replica can actually handle well — set it too high and replicas get overloaded before scaling triggers, as covered in the Envoy scaling troubleshooting post on this site.

  5. Load test at the resource allocation you plan to ship

    Capacity planning done on paper rarely survives contact with real traffic patterns. Run a load test against the actual CPU/memory allocation and scale rule configuration you intend to use in production, watching both replica count and per-replica resource utilization during the test.

  6. Revisit sizing after real production traffic accumulates

    Use the ACA KQL primer on this site to query actual replica counts and scaling events over a real traffic window, and compare against your planned allocation — initial sizing is a starting point, not a permanent setting.

Result: a resource allocation and replica range chosen deliberately rather than left at defaults — the single biggest lever for avoiding both under-provisioned throttling and over-provisioned idle cost in Container Apps.
