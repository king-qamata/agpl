Troubleshooting Python Deployments on App Service Linux: When Oryx Silently Skips Your Build

Python Oryx 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A deployment to a Python App Service Linux app reports success in the pipeline, but the app continues serving old behavior — a bug fix doesn't take effect, or a newly added dependency causes an ImportError at runtime even though it's listed in requirements.txt and the deployment "succeeded."

02Environment

  • Python app on App Service Linux, built via Oryx (Azure's build system for code-based, non-container deployments)
  • Deployment via ZipDeploy, GitHub Actions, or Azure DevOps
  • Recently changed requirements.txt, Python version, or build configuration

03Diagnosis

Oryx decides whether to run a build (create a new virtual environment and install dependencies) based on specific triggers and settings — it doesn't unconditionally rebuild on every deployment. If those triggers don't fire the way you expect, your zip package gets deployed as-is without a fresh pip install, and the app runs against whatever virtual environment already existed.

  • Check the deployment log for actual build output — look specifically for Oryx's "Running pip install" step in the Kudu deployment log, not just a generic "deployment successful" message. If that step is missing or skipped, no rebuild happened.
  • Check SCM_DO_BUILD_DURING_DEPLOYMENT — if this app setting is explicitly set to false, Oryx won't build at all regardless of what changed.
  • Check whether you're deploying via Run-From-Package — this deployment mode changes how and where dependencies are expected to already be built, and mixing it with an assumption of Oryx doing a fresh build on every deploy is a common source of confusion.
bash — confirm the build setting
az webapp config appsettings list --name my-app --resource-group my-rg --query "[?name=='SCM_DO_BUILD_DURING_DEPLOYMENT']"
Common misdiagnosis: a deployment that "succeeds" but doesn't reflect code changes is often mistaken for a caching issue (browser cache, CDN cache) when the actual cause is that the new code and dependencies were never built into the running environment in the first place.

04Root Cause

Oryx's build behavior is controlled by specific settings and deployment method, not an unconditional "always rebuild" default. A deployment method or setting that skips the build step (Run-From-Package expecting pre-built dependencies, or SCM_DO_BUILD_DURING_DEPLOYMENT set to false) produces a "successful" deployment that's really just a file copy — the app then runs against whatever Python environment was already present, which may not include your latest changes.

05Fix

  • Explicitly enable the build step by setting SCM_DO_BUILD_DURING_DEPLOYMENT=true if you want Oryx to build on every deployment via ZipDeploy.
  • If using Run-From-Package, build dependencies into the package before deployment (as part of your CI pipeline) rather than expecting Oryx to build them post-deployment — these are two different models and shouldn't be mixed.
  • Verify the build actually ran by checking the Kudu deployment log for the specific pip install step after every deployment during initial pipeline setup, until you're confident the configuration is correct.
  • Pin your Python version explicitly in app settings (PYTHON_VERSION or the linux_fx_version) to avoid Oryx selecting a different interpreter version than you tested against, which can also cause dependency resolution differences.
Prevention tip: add a simple version or build-timestamp endpoint to your app that you can check immediately after every deployment — this catches "deployment succeeded but nothing actually changed" issues immediately rather than after a confusing bug report.
