Node.js Functions: Diagnosing require() Overhead on Cold Start

Node.js Cold Start 6 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A Node.js Function's cold start is slower than expected given how little the function handler itself actually does. The gap between "function is simple" and "cold start is slow" is the tell — this is a different pattern from the general cold start behavior covered in the main cold start post on this site.

02Environment

  • Node.js on Azure Functions, any plan
  • Function file has multiple top-level require()/import statements, some pulling in large SDKs or frameworks
  • Large node_modules tree, possibly with dependencies not actually used by every function in a multi-function app

03Diagnosis

Node's module system executes a module's top-level code the first time it's required — including any expensive initialization inside that module. On a cold start, every require() at the top of your entry file runs before your handler code executes, and heavy SDKs (large cloud SDKs, ORMs, bundling many sub-clients) can have meaningful load time.

  • Add simple timing instrumentation around your top-level requires locally to see which import dominates.
  • Check whether a multi-function app is importing dependencies at the shared module level that only one specific function actually needs — this cost gets paid by every function's cold start, not just the one that uses it.
bash — quick local timing check
node -e "console.time('require'); require('./index.js'); console.timeEnd('require')"
Common misdiagnosis: slow Node.js cold starts are sometimes attributed generally to "the platform" without checking what's actually happening during module load. Since Node.js is generally fast to start, an unusually slow cold start is a strong signal that something specific in the require graph is the cost, not baseline platform overhead.

04Root Cause

Every require() at the top of a Node.js entry file executes synchronously and completely before anything else in that file runs, including the exported handler. Large SDKs that initialize substantial internal state at require time, or a shared module in a multi-function app that imports dependencies not needed by every function using it, both add fixed cost to every cold start regardless of which specific function is actually being invoked.

05Fix

  • Move rarely-used, heavy requires inside the function body so the cost is only paid on invocations that actually need that dependency, not on every cold start.
  • Split shared modules by actual usage in multi-function apps — avoid one large shared file that every function imports if most functions only need a small piece of it.
  • Import specific submodules rather than entire SDKs where the SDK supports it (e.g. importing a single AWS/Azure SDK client rather than the full package) to reduce what needs to load.
  • Consider a Premium plan with always-ready instances if the dependency set is genuinely required and latency is customer-facing — the same trade-off as the Python and .NET cold start posts on this site.
Prevention tip: periodically audit the entry file's top-level requires as dependencies are added over time — it's easy for an initially lean function to accumulate unnecessary eager imports as the codebase grows, especially in multi-function apps sharing common modules.
