Deploying a Container Instance into a Virtual Network

ACI VNet 7 min read

By default, Azure Container Instances get a public IP and no private network access. If a container needs to reach a database, storage account, or another resource that's locked to private networking, it needs to run inside a VNet — this walks through that specific deployment shape, as covered in the ACI vs Web App vs ACA decision guide on this site.

Before you start
  • An existing VNet with an available address space for a new subnet
  • Azure CLI signed in

  1. Create a dedicated subnet for container groups

    ACI requires its own delegated subnet — it can't share a subnet with other resource types like VMs. Create one sized for how many container groups you expect to run concurrently.

    bash
    az network vnet subnet create \
  --resource-group rg-myapp \
  --vnet-name my-vnet \
  --name aci-subnet \
  --address-prefixes 10.0.1.0/24 \
  --delegations Microsoft.ContainerInstance/containerGroups

  2. Deploy the container group into the subnet

    Reference the VNet and subnet directly in the container group creation call — this is what removes the public IP and places the container's networking inside your VNet instead.

    bash
    az container create \
  --resource-group rg-myapp \
  --name my-private-container \
  --image myregistry.azurecr.io/myapp:latest \
  --vnet my-vnet \
  --subnet aci-subnet \
  --cpu 1 --memory 1.5

  3. Confirm there's no public IP

    A VNet-deployed container group has only a private IP within the subnet — verify this rather than assuming, since a misconfigured deployment can silently fall back to public networking in some scenarios.

    bash
    az container show --resource-group rg-myapp --name my-private-container --query ipAddress

  4. Test reachability from inside the VNet

    From another resource in the same VNet (a VM, or a different container group in the same or a peered subnet), confirm you can reach the private container on its exposed port — this is the actual proof the networking is set up correctly, not just the absence of a public IP.

  5. Add DNS if needed

    Unlike public ACI deployments, a VNet-deployed container group doesn't get a public DNS name — if other resources need to reach it by name rather than IP, add a Private DNS Zone record pointing at its private IP.

Result: a container group reachable only from within your VNet — no public exposure, and able to reach other private resources on the same network, which is the main reason to choose this deployment shape over a plain public ACI container.
