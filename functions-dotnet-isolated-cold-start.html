.NET Isolated Worker Cold Starts: Why They're Slower Than In-Process

.NET Isolated Cold Start 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

After migrating a Function App from the in-process .NET model to the isolated worker model (required for newer .NET versions), cold start times get noticeably worse — not marginally, often by a meaningful multiple — even though the application code itself is largely unchanged.

02Environment

  • Azure Functions on .NET, recently migrated from in-process to isolated worker model
  • Consumption or Premium plan where cold start behavior is customer-visible
  • Same trigger types and general workload shape as before migration

03Diagnosis

Compare cold start duration before and after the migration using the same KQL pattern from the cold start troubleshooting post on this site — filter to invocations following an idle period and look at the duration distribution. A consistent, substantial increase specifically correlated with the isolated-worker migration (not a code change, not a traffic pattern change) points at the hosting model itself as the cause.

KQL — compare cold start duration across a migration date
requests
| where timestamp > ago(14d)
| where duration > 2000
| summarize avg(duration), count() by bin(timestamp, 1d)
| order by timestamp asc
Common misdiagnosis: a cold start regression after a .NET version upgrade is often attributed to the new .NET version itself being slower, when the isolated worker model — not the .NET version — is usually the larger factor. Teams sometimes spend time trying older/newer .NET minor versions without addressing the actual structural cause.

04Root Cause

The isolated worker model runs your function code in a separate process from the Functions host, communicating over gRPC — this is what enables full control over the .NET version and middleware pipeline, but it also means a cold start now has to start two processes and establish that communication channel, rather than loading your code directly into the host process as the in-process model does. That additional process boundary is the structural source of the extra cold start latency, not a regression in .NET itself.

05Fix

  • If cold start latency is customer-critical, move to Premium plan with always-ready instances — this is the most reliable way to eliminate the isolated-worker cold start penalty rather than trying to minimize it on Consumption.
  • Trim startup work in Program.cs — minimize what runs during host and DI container initialization, since this now happens across the process boundary on every cold start.
  • Use ReadyToRun (R2R) compilation for your deployment, which precompiles IL to native code and measurably reduces isolated worker startup time compared to a standard build.
  • If in-process is still viable for your .NET version, weigh whether you actually need isolated-worker-specific features (custom middleware, non-LTS .NET versions) against the cold start cost — in-process remains meaningfully faster to cold start where it's still supported.
Prevention tip: if evaluating a move to isolated worker ahead of an in-process deprecation deadline, benchmark cold start behavior specifically — not just functional correctness — before committing, so the latency change is a planned trade-off rather than a surprise found in production.
