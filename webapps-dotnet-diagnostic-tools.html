Installing Diagnostic Tools in .NET Core Custom Container Images

.NET Custom Containers 6 min read

The Kudu Process Explorer approach used in the App Service high CPU post on this site works well for the platform-managed .NET runtime, but a custom container image doesn't automatically include the .NET diagnostic tooling. This adds it in.

Before you start
  • An existing Dockerfile for a .NET app deployed as a custom container to App Service or Container Apps

  1. Add the diagnostic tools to your Dockerfile

    Install the .NET diagnostic global tools in your image — dotnet-trace for CPU/event tracing, dotnet-dump for memory dump collection and analysis, and dotnet-counters for live performance counters.

    Dockerfile
    RUN dotnet tool install --global dotnet-trace
RUN dotnet tool install --global dotnet-dump
RUN dotnet tool install --global dotnet-counters
ENV PATH="${PATH}:/root/.dotnet/tools"

  2. Get a shell into the running container

    For App Service, use the Kudu SSH/console feature for custom containers. For Container Apps, use the portal's console feature or az containerapp exec.

    bash — Container Apps
    az containerapp exec --name my-app --resource-group my-rg --command /bin/bash

  3. Capture a CPU trace during high load

    Find the running process ID and collect a trace while the issue is reproducing — this is the .NET equivalent of the Windows Process Explorer flow used elsewhere on this site.

    bash
    dotnet-trace ps
dotnet-trace collect --process-id <pid> --duration 00:00:30

  4. Capture a memory dump for leak investigation

    Same pattern as the Windows memory leak post on this site, but for a Linux container using dotnet-dump instead of WinDbg.

    bash
    dotnet-dump collect --process-id <pid>

  5. Watch live counters for a quick health check

    For a fast, low-overhead check before reaching for a full trace or dump, dotnet-counters shows live GC, thread pool, and request metrics streaming in the terminal.

    bash
    dotnet-counters monitor --process-id <pid>

  6. Copy artifacts out for offline analysis

    Trace and dump files are usually best analyzed outside the container — copy them out via az containerapp exec file transfer or Kudu's file browser, then open the trace in a tool like PerfView or Visual Studio, and the dump with dotnet-dump analyze or a full debugger.

Result: the same class of diagnostics available on the platform-managed .NET runtime, now available inside a custom container image — useful the moment an issue only reproduces under the exact conditions of your custom image.
