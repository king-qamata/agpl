Mounting an Azure Files Share into a Container Instance

ACI Azure Files 6 min read

A container group's own filesystem is ephemeral — it's gone the moment the container restarts or the group is recreated. For any workload that needs to persist files (a batch job writing output, an SFTP-style file drop, config that should survive a restart), mounting an Azure Files share is the standard fix.

Before you start
  • An existing Storage Account with a File Share created
  • Azure CLI signed in

  1. Get the storage account name and key

    ACI's Azure Files mount uses the storage account key directly at deployment time — store this securely and avoid putting it in scripts checked into source control.

    bash
    az storage account keys list \
  --resource-group rg-myapp \
  --account-name mystorageacct \
  --query "[0].value" -o tsv

  2. Deploy the container with the volume mount

    Specify the Azure Files share, storage account, and key together with the mount path inside the container.

    bash
    az container create \
  --resource-group rg-myapp \
  --name my-container-with-storage \
  --image myregistry.azurecr.io/myapp:latest \
  --azure-file-volume-account-name mystorageacct \
  --azure-file-volume-account-key <storage-key> \
  --azure-file-volume-share-name myshare \
  --azure-file-volume-mount-path /mnt/data

  3. Verify the mount from inside the container

    Exec into the running container and confirm the mount path is populated with the share's existing contents, and that a write from inside the container appears in the share.

    bash
    az container exec --resource-group rg-myapp --name my-container-with-storage --exec-command "/bin/sh"
# inside the container:
ls /mnt/data
echo "test" > /mnt/data/test.txt

  4. Confirm persistence across a restart

    Restart the container group and confirm the file written in the previous step is still present — this is the actual proof the mount is backed by durable storage rather than the container's own ephemeral filesystem.

  5. Consider identity-based access as a follow-up

    Storage account keys work but carry the same long-lived-secret trade-off covered in the Managed Identity posts elsewhere on this site — for a production workload, evaluate whether your scenario can move to identity-based storage access instead of an account key mount.

Result: a container group with a persistent, shared filesystem mount — necessary for any ACI workload where the container's own ephemeral disk isn't sufficient, like batch processing output or file-drop scenarios.
