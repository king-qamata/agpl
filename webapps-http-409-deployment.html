Troubleshooting HTTP 409s When Deploying to App Service

Kudu CI/CD 6 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A deployment pipeline (Azure DevOps, GitHub Actions, or a direct CLI deploy) fails with a 409 Conflict, or the deployment task reports a 503 from the remote server. It's intermittent — the same pipeline configuration sometimes succeeds and sometimes fails, often correlating with how frequently deployments are triggered.

02Environment

  • App Service (Windows or Linux), deployed via Kudu's deployment API (ZipDeploy, MSDeploy, or similar)
  • CI/CD pipeline that can trigger overlapping deployments — parallel pipeline runs, rapid successive commits, or multiple deployment slots deploying near-simultaneously

03Diagnosis

Kudu does not support concurrent deployments to the same app — it creates a lock file during a deployment specifically to prevent two deployments from corrupting each other's state. A second deployment arriving while one is already in progress gets rejected, which surfaces in your pipeline as a 409 or a 503 depending on exactly when it hits the lock.

  • Check whether your pipeline can trigger multiple runs concurrently — for example, two commits pushed close together both kicking off a deploy stage without queuing.
  • Check Kudu's deployment log (https://<app>.scm.azurewebsites.net/api/deployments) for overlapping timestamps between a failed deployment and one that was in progress.
  • If deployments are failing consistently rather than intermittently, also check whether high memory usage on the instance is causing the Kudu container itself to fail to start — a different cause with the same symptom.
Common misdiagnosis: an intermittent 409/503 during deployment is sometimes reported as "Azure DevOps is flaky" or "the App Service is unreliable." In the large majority of cases it's a straightforward concurrency conflict at the Kudu deployment lock, not a platform reliability issue.

04Root Cause

Kudu serializes deployments using a lock file to avoid inconsistent state from two deployments writing to the same app simultaneously. Pipelines that allow concurrent runs — whether from parallel triggers, rapid successive pushes without queuing, or multiple slots deploying near-simultaneously — will occasionally have two deployments overlap, and the second one hits the lock and fails.

05Fix

  • Enforce serial deployment in your pipeline. Most CI/CD platforms support limiting concurrency per environment/stage (e.g. a deployment queue or concurrency group) — configure this so overlapping runs queue instead of racing.
  • Add retry logic with backoff to the deployment step itself, so a transient lock conflict from a near-simultaneous deployment resolves automatically on retry rather than failing the whole pipeline run.
  • If using deployment slots, stagger deployments to different slots rather than triggering them at the exact same time, even though they're technically independent app instances sharing the same Kudu deployment infrastructure pattern.
  • Rule out the memory-related cause separately — if Kudu itself is failing to start due to high memory on the instance, that needs a different fix (scaling, or addressing the memory pressure) rather than pipeline concurrency changes.
Prevention tip: configure your CI/CD platform's built-in concurrency controls for deployment stages from the start, rather than discovering the lock conflict the first time two team members deploy close together.
