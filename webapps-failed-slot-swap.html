Failed Slot Swap: Diagnosing "Cannot Swap Site Slots" Errors

Deployment Slots App Service Linux 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A slot swap (staging → production, or between any two named slots) fails outright with an error like "Cannot swap site slots for site '<app>' because the operation timed out" or a generic swap failure, rather than completing. The staging slot may look fine when browsed directly.

02Environment

  • App Service Linux (or Windows) using deployment slots
  • Swap initiated via portal, Azure CLI, or a CI/CD pipeline step
  • App may have custom startup logic, warm-up requests, or App Settings that differ between slots

03Diagnosis

A swap isn't just a DNS-style pointer flip — Azure first triggers the target slot's application to restart with the swapped configuration and waits for it to report healthy before completing. If the app doesn't come up cleanly under that specific condition, the swap fails rather than proceeding with a broken app in production.

  • Check for slot-specific settings incorrectly marked "slot sticky." A setting that should swap (like a feature flag) but is marked sticky won't move with the swap, potentially causing the app to start with unexpected configuration in its new slot.
  • Look at what actually differs between slots beyond just application settings — connection strings, WEBSITE_RUN_FROM_PACKAGE, or any environment-specific value that could cause the app to fail its startup check under the "swapped" configuration specifically.
  • Check Kudu/Log Stream for the target slot during the swap window — the swap operation itself triggers a restart, and if the app crashes or times out on startup in that moment, that's the actual failure, surfaced by the platform as a generic swap error.
Common misdiagnosis: a failed swap is often retried repeatedly assuming it's a transient platform issue. If the same swap fails consistently, the app itself is failing its post-swap health check — retrying without investigating the app's behavior under swapped configuration won't help.

04Root Cause

Azure performs a swap by applying the target slot's configuration to the app and waiting for it to restart successfully — this is what "warm-up" during a swap actually verifies. If the app fails to start cleanly under the post-swap configuration (a missing setting, a connection string pointing somewhere unreachable, a slot-sticky setting that should have swapped but didn't), the health check fails and Azure aborts the swap rather than completing it against a broken app.

05Fix

  • Audit slot-sticky settings — confirm only genuinely environment-specific values (like a slot's own connection string) are marked sticky, and everything else is allowed to swap normally.
  • Test the exact post-swap configuration in staging first — apply what would be the swapped configuration to the staging slot directly and confirm the app starts cleanly before attempting the real swap.
  • Add or check swap warm-up settings (applicationInitialization configuration) to ensure the platform waits long enough and hits the right warm-up path before deciding the app is healthy.
  • Review Kudu logs from the failed swap window specifically, not just general application logs, to see what the app was doing at the moment the swap was attempted.
Prevention tip: before relying on slot swaps for zero-downtime deployments, explicitly test what happens when staging is swapped with production's exact configuration differences — don't assume "it works when I browse staging directly" is equivalent to "it will pass its swap health check."
