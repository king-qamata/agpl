Configuring a Local Redis Cache to Cut Database Load on Linux App Service

Intermediate Azure Cache for Redis 7 min read

Repeated expensive queries or computations are a common contributor to the high-CPU and slow-response patterns covered elsewhere on this site. This walks through provisioning Azure Cache for Redis and wiring it into a Linux App Service app as a caching layer in front of a database.

Before you start
  • An existing Linux App Service running an app with a database-backed hot path
  • Azure CLI signed in

  1. Provision the cache

    Create a Basic or Standard tier Azure Cache for Redis instance in the same region as your App Service — same-region placement matters for latency, since a cache is only useful if it's meaningfully faster than the database call it's replacing.

    bash
    az redis create \
  --name my-app-cache \
  --resource-group rg-myapp \
  --location eastus \
  --sku Basic \
  --vm-size c0

  2. Get the connection details

    Retrieve the hostname and access key, and store the access key in Key Vault or as an App Service application setting — never hardcode it in source.

    bash
    az redis show --name my-app-cache --resource-group rg-myapp --query hostName
az redis list-keys --name my-app-cache --resource-group rg-myapp

  3. Add the connection string as an app setting

    Set it on the App Service so your app can read it from the environment at runtime, consistent with how the rest of your configuration is managed.

    bash
    az webapp config appsettings set \
  --name my-app \
  --resource-group rg-myapp \
  --settings REDIS_CONNECTION="my-app-cache.redis.cache.windows.net:6380,password=<key>,ssl=True"

  4. Wire caching around the expensive call

    In application code, wrap the expensive query or computation with a cache-aside pattern: check the cache first, fall back to the database on a miss, then populate the cache with an appropriate expiration (TTL) before returning.

    Pattern — cache-aside
    value = cache.get(key)
if value is None:
    value = database.query(...)
    cache.set(key, value, ttl=300)
return value

  5. Choose sensible TTLs and eviction

    Pick a TTL that reflects how often the underlying data actually changes — too short and you barely reduce database load; too long and users see stale data. For data that changes on specific events (e.g. a write), consider actively invalidating the cache key at that point instead of relying on TTL alone.

  6. Verify with KQL

    After deployment, confirm database call volume actually dropped by comparing before/after request telemetry — see the KQL fundamentals tutorial for the query pattern to compare traffic and latency across a time window.

Result: a working cache-aside layer in front of your database's hottest queries — the same kind of fix referenced as an option in this site's App Service high CPU post.
