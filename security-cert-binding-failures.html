Certificate Binding Failures After a Custom Domain Migration

TLS/SSL Application Gateway 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

Browsers show a certificate error (untrusted, name mismatch, or "provided by a certificate authority that is not trusted") immediately after migrating a custom domain to a new binding — a new App Service custom domain, a new Application Gateway listener, or a new Front Door endpoint — even though the certificate itself was valid and working under the previous configuration.

02Environment

  • Custom domain recently repointed to a new Azure resource (App Service, App Gateway, or Front Door)
  • TLS certificate either uploaded manually (PFX) or issued via App Service Managed Certificate / Key Vault reference
  • DNS recently changed (CNAME or A record) as part of the same migration

03Diagnosis

Separate "certificate is wrong" from "certificate isn't being served at all" — they have different causes and the browser's exact error message tells you which:

  • Name mismatch error ("certificate is only valid for X"): the connection is landing on the wrong resource — check DNS is actually pointing at the new target and has propagated, not still resolving to the old one.
  • Untrusted / incomplete chain error: the certificate is reaching the browser but missing intermediate certificates. Check with an external SSL checker or openssl s_client -connect yourdomain.com:443 -showcerts to see the full chain being presented.
  • Wrong certificate being served on a shared resource: on App Gateway or Front Door serving multiple hostnames, confirm SNI-based routing is configured correctly and the new hostname is bound to the correct listener/certificate pair, not falling through to a default.
bash — check what certificate chain is actually being served
openssl s_client -connect yourdomain.com:443 -servername yourdomain.com -showcerts </dev/null 2>/dev/null | openssl x509 -noout -subject -issuer -dates
Common misdiagnosis: teams often re-upload or re-issue the certificate first, assuming it expired or corrupted during migration. If the certificate worked before the migration and nothing about the cert itself changed, the far more likely cause is routing (DNS/SNI) or an incomplete chain — not the certificate's validity.

04Root Cause

Migrations that change where a domain's traffic terminates TLS often leave one piece behind: DNS still pointing at the old target during propagation, a certificate bound to the old resource but not re-bound to the new one, or an intermediate certificate that was present in the old resource's trust store but wasn't uploaded again to the new one. Any of these produces a certificate error even though the leaf certificate itself is completely valid.

05Fix

  • Confirm DNS first: verify the domain resolves to the new target from multiple locations/resolvers before troubleshooting anything TLS-specific — a stale DNS cache will make a correctly configured new binding look broken.
  • Re-bind the certificate explicitly on the new resource (App Service custom domain TLS binding, App Gateway listener, or Front Door endpoint) rather than assuming it carried over from the old one.
  • Upload the full chain, not just the leaf certificate — most PFX export tools include intermediates automatically, but manually assembled certificate bundles sometimes omit them.
  • For multi-hostname App Gateway/Front Door setups, double check SNI listener configuration maps the new hostname to the correct certificate — a fallback to a default/self-signed certificate under SNI misconfiguration produces exactly this kind of error.
Prevention tip: when migrating a custom domain, validate the full chain with an external checker (or the openssl command above) against the new target directly by IP before cutting DNS over — this isolates certificate/binding issues from DNS propagation timing, so you're not debugging two variables at once.
