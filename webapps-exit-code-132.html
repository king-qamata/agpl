Container Crash with Exit Code 132 (SIGILL): Diagnosing Invalid CPU Instructions

Web App for Containers App Service Linux 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A custom container deployed to Web App for Containers (or App Service Linux) crashes immediately on startup, or shortly after handling its first request. The container logs show the process terminating with exit code 132, with no application-level stack trace or exception — the process simply disappears.

02Environment

  • Web App for Containers running a custom Docker image
  • Image built or pulled on a different CPU architecture or host than the one it now runs on
  • Often follows a base image update, a move to a "blessed"/Microsoft-maintained base image, or a build pipeline running on different hardware than production

03Diagnosis

Exit code 132 corresponds to signal 4 (128 + 4 = 132), which is SIGILL — Illegal Instruction. This is a CPU-level fault, not an application bug: the process attempted to execute a machine instruction that the underlying processor doesn't support.

  • Check the container platform logs (not just app logs) for the exit code and signal name.
  • Confirm what CPU architecture and instruction set the image was built for versus what the App Service host actually provides — this mismatch is the most common cause.
  • If the image was recently rebuilt on a newer machine (e.g. one supporting AVX-512 or other extended instruction sets), that's the first thing to suspect.
Common misdiagnosis: because there's no application stack trace, teams often assume the app crashed due to a code bug and start bisecting recent code changes. SIGILL happens below the application layer entirely — the app never gets far enough to log anything meaningful.

04Root Cause

The container image (or a native dependency/binary inside it, such as a compiled library) was compiled with instructions targeting a newer or different CPU microarchitecture than what's available on the App Service compute powering the container. When the CPU hits an unsupported instruction, the kernel delivers SIGILL and the process is killed immediately — this is a hardware compatibility issue baked into the image, not a runtime configuration problem.

05Fix

  • Rebuild on a compatible target: use a build environment that targets a broadly compatible instruction set (e.g. build with generic x86-64 targeting rather than -march=native or similar CPU-specific compiler flags).
  • Pin your base image: use a specific, known-good tag for your base image rather than latest, so a base image update doesn't silently change the compiled binaries underneath you.
  • Check native dependencies: if the crash is in a compiled library (e.g. a Python or Node native extension), rebuild or replace that dependency with a build compatible with the hosting environment.
  • Verify locally against matching hardware: where possible, test the image in an environment that matches production CPU capabilities before pushing to the registry.
Prevention tip: add an explicit CPU/architecture compatibility check to your CI build pipeline, and avoid CPU-specific optimization flags in Dockerfiles meant for cloud deployment — portability should generally win over marginal performance gains from CPU-specific instructions.
