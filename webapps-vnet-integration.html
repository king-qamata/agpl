VNET Integration Failures: Common Misconfigurations

Regional VNET Integration Networking 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

An App Service configured with Regional VNET Integration can't reach a resource inside the VNET — commonly a private database, an internal API, or a resource behind a private endpoint — even though the integration shows as "Connected" in the portal and outbound traffic to public internet destinations works fine.

02Environment

  • App Service with Regional VNET Integration enabled, connected to a delegated subnet
  • Target resource is inside the same VNET, a peered VNET, or reachable only via a private endpoint
  • Possibly a custom route table (UDR) applied to the integration subnet

03Diagnosis

"Connected" in the portal only confirms the integration itself was provisioned — it does not confirm traffic is actually routing correctly. Work through these in order:

  • Confirm the subnet is properly delegated to Microsoft.Web/serverFarms and isn't shared with another resource type that could conflict.
  • Check "Route All" configuration. By default, only traffic destined for private IP ranges routes through the VNET; if you need all outbound traffic (including internet-bound) to go through the VNET, that has to be explicitly enabled.
  • Verify DNS resolution. If the target is a private endpoint, the App Service needs to resolve its private DNS name correctly — check whether a custom DNS server or private DNS zone is linked to the VNET, and whether the App Service is configured to use it.
  • Check for a conflicting route table (UDR) on the integration subnet that might be sending traffic somewhere unexpected, such as through a firewall or NVA that isn't configured to allow the destination.
bash — quick DNS resolution check from Kudu console
nameresolver internal-db.privatelink.database.windows.net
Common misdiagnosis: teams often assume the integration itself is broken and try recreating it, when the actual issue is DNS resolution returning the resource's public IP instead of its private one — the connection then fails or times out at the network layer, not because the VNET integration failed.

04Root Cause

VNET Integration failures are rarely about the integration itself — they're almost always one of three things: the subnet delegation or route configuration doesn't send the right traffic through the VNET, DNS resolves to the wrong (public) address so the app never even attempts to use the private path, or a route table redirects traffic through a network appliance that isn't configured to permit it.

05Fix

  • Fix delegation: ensure the integration subnet is delegated solely to Microsoft.Web/serverFarms.
  • Enable Route All if needed: turn on "Route All" under the VNET Integration networking settings if traffic other than RFC1918 private ranges also needs to traverse the VNET.
  • Fix DNS: link the correct private DNS zone to the VNET, and if using a custom DNS server, configure the App Service's DNS settings to point to it explicitly rather than relying on Azure-provided DNS.
  • Audit route tables: review any UDR applied to the integration subnet for unintended routes, and confirm any NVA or firewall in the path explicitly allows the destination.
Prevention tip: after any VNET Integration change, test connectivity from the Kudu console (SSH or the console tab) rather than only checking the portal's connection status — the portal confirms provisioning, not actual reachability.
