Configuring Autoscale Rules Based on CPU and Queue Length

Intermediate Autoscale 7 min read

CPU-only autoscale rules react too slowly for workloads with bursty, queue-driven traffic — by the time CPU climbs, users have already felt it. This walks through combining a CPU rule with a queue length rule so scaling reacts to demand building up, not just resource pressure that's already arrived.

Before you start
  • An App Service on a Standard tier or higher (autoscale requires this)
  • A Storage Queue or Service Bus queue your app processes work from, if using the queue-based rule

  1. Open the scale-out settings

    In the portal, go to your App Service Plan → Scale out (App Service plan). Switch from "Manual scale" to Custom autoscale.

  2. Add the CPU-based scale-out rule

    Under the default scale condition, add a rule: Metric = CPU Percentage, aggregation over the last 10 minutes, operator "Greater than", threshold around 70%, action "Increase count by 1", with a cooldown of 5 minutes.

  3. Add the corresponding scale-in rule

    Add a second rule for the same metric: "Less than" a lower threshold (e.g. 30%), action "Decrease count by 1", with a longer cooldown (e.g. 10 minutes) — scaling in more cautiously than scaling out avoids flapping.

  4. Add a queue length rule

    If your app processes background work from a queue, add a Custom metric source pointing at the Storage Queue or Service Bus namespace, metric "Approximate Message Count" (or the queue-specific equivalent), threshold set to whatever backlog size represents "falling behind" for your workload — this reacts to demand building up before CPU necessarily reflects it.

    Reasoning — why combine both
    CPU rule:   reacts to compute pressure already happening
Queue rule: reacts to backlog building, often *before* CPU rises
Together:   scale-out triggers on whichever signal fires first

  5. Set instance limits

    Configure minimum and maximum instance counts for the scale condition — a minimum above 1 avoids a cold single instance handling a traffic spike alone, and a maximum protects against runaway cost from a misbehaving rule or genuine traffic anomaly.

  6. Watch the Run history

    After deploying, check the Run history tab over the following days to confirm the rules are firing as expected and not flapping (repeatedly scaling in and out). Adjust cooldowns or thresholds if you see oscillation.

Result: autoscale that responds to both resource pressure and workload backlog, with cooldowns tuned to avoid the flapping that makes teams distrust autoscale in the first place.
