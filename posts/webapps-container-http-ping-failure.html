Container Didn't Respond to HTTP Pings on Port: Diagnosing Failed Site Starts

Web App for Containers Startup 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

Site start fails with an error along the lines of "Container didn't respond to HTTP pings on port <port>." The container image builds and deploys successfully, and the same image may even run fine locally with docker run — the failure is specific to App Service's own startup verification.

02Environment

  • Web App for Containers on App Service Linux
  • Custom container image, recently deployed or recently modified
  • Application inside the container may have a non-trivial startup sequence (migrations, cache warming, dependency initialization)

03Diagnosis

App Service pings the container on a specific port after starting it, and expects an HTTP response within a bounded startup window — if that doesn't happen, it considers the container failed regardless of whether the app would have eventually come up. Work through these in order:

  • Confirm the app actually listens on the port App Service expects. By default this is port 80 unless WEBSITES_PORT is explicitly set to match whatever port your app binds to — a mismatch here is the single most common cause.
  • Confirm the app binds to all interfaces, not just localhost. An app listening on 127.0.0.1 instead of 0.0.0.0 is unreachable from outside its own network namespace, which is effectively how App Service's ping reaches it.
  • Check how long startup actually takes. If the app has a genuinely slow startup sequence (large migrations, heavy cache warming), it may simply not be ready within the platform's default ping window.
  • Check container logs from the failed start attempt via Log Stream or Kudu — confirm the app process is even starting successfully inside the container, as opposed to crashing before it would ever bind to a port.
Common misdiagnosis: because the image works fine with a local docker run, this is sometimes treated as an Azure platform issue. Locally there's no equivalent of the startup ping timeout — the container just runs. The platform's specific expectations around port and readiness timing are what's different, not the container image itself.

04Root Cause

App Service needs to confirm a container is actually serving traffic before routing requests to it, and does this via an HTTP ping to a configured port within a startup time budget. A port mismatch, binding only to localhost, or a startup sequence that genuinely exceeds the ping window all produce the same "didn't respond" failure, even though the underlying causes are different — a wrong port is a configuration bug, while a slow startup is a timing problem that needs a different fix.

05Fix

  • Set WEBSITES_PORT explicitly to match whatever port your app actually binds to, if it isn't 80.
  • Bind to 0.0.0.0 rather than localhost/127.0.0.1 in your application's server configuration.
  • If startup is genuinely slow, increase the startup time budget via the WEBSITES_CONTAINER_START_TIME_LIMIT app setting, and separately consider whether startup work (migrations, cache warming) can be moved out of the request-serving container's critical path.
  • Add a lightweight readiness endpoint that responds quickly even while heavier initialization continues in the background, if your app architecture allows separating "process is up" from "fully ready to serve real traffic."
Prevention tip: test any new container image against App Service's actual startup ping behavior — not just a local docker run — before treating a deployment as validated, since the local test doesn't exercise the specific port/timing expectations that cause this failure in production.
