ACI Container Group Stuck in Pending: Diagnosing Subnet Delegation Issues

ACI VNet 6 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A container group deployed with --vnet/--subnet stays in Pending state indefinitely, never transitioning to Running. There's often no detailed error in the portal beyond the stuck state itself.

02Environment

  • Azure Container Instances deployed into an existing VNet subnet, following the pattern in the VNet deployment tutorial on this site
  • Subnet may be shared, recently created, or reused from another purpose

03Diagnosis

Two specific subnet conditions account for the large majority of stuck-Pending ACI deployments:

  • Missing or incorrect delegation. The subnet must be delegated specifically to Microsoft.ContainerInstance/containerGroups — check this on the subnet's configuration, not just that a delegation exists (a delegation to a different service doesn't work).
  • No available IP addresses. ACI consumes a private IP per container group from the subnet's address range — a small subnet that's already hosting other resources or previous container groups can run out of free addresses, silently blocking new deployments from ever provisioning.
bash — check subnet delegation
az network vnet subnet show \
  --resource-group rg-myapp \
  --vnet-name my-vnet \
  --name aci-subnet \
  --query delegations
Common misdiagnosis: a stuck Pending deployment is sometimes retried repeatedly assuming it's a transient platform issue. If the subnet's delegation or address space is the actual blocker, retrying the same deployment will fail the same way indefinitely — the fix has to happen at the subnet level.

04Root Cause

Container groups deployed into a VNet require a subnet dedicated to ACI via explicit delegation — this reserves the subnet specifically for container group networking rather than general-purpose VM or other resource use. Without correct delegation, or without free address space in that subnet, ACI can't complete the networking setup needed to bring the container group to a running state, and it stalls in Pending rather than failing with an immediately obvious error.

05Fix

  • Add or correct the delegation on the target subnet to Microsoft.ContainerInstance/containerGroups if missing or set to the wrong service.
  • Check subnet size against actual usage — if the subnet is small (e.g. a /28) and already has other resources or container groups using addresses, either expand the subnet or move to a dedicated, appropriately sized one.
  • Use a subnet dedicated solely to ACI rather than sharing it with other resource types, both to avoid delegation conflicts and to make capacity planning simpler.
  • Delete and redeploy the stuck container group after fixing the subnet — a Pending deployment generally doesn't self-recover once the underlying subnet issue is fixed; it needs a fresh deployment attempt.
Prevention tip: size the ACI subnet with real headroom above your expected concurrent container group count, and keep it dedicated to ACI only — this avoids both the delegation conflict and the address exhaustion versions of this problem before they happen.
