Scaling Rules Not Triggering: Debugging the Envoy Proxy Layer

KEDA Envoy Ingress 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

An HTTP scale rule is configured on a Container App, real traffic is clearly arriving (client-side logs, an external monitor, or a load test confirm requests are being sent), but the app never scales past its minimum replica count. No errors appear anywhere — the app just silently stays flat.

02Environment

  • Azure Container Apps with an HTTP-based scale rule (concurrent requests threshold)
  • Traffic arriving through the app's external or internal ingress
  • Possibly fronted by Azure Front Door, Application Gateway, or another proxy in front of the Container App

03Diagnosis

Container Apps' HTTP scaling is driven by concurrent request counts observed at the Envoy-based ingress proxy in front of each revision — not by a metric you compute externally. The two most common gaps between "traffic is happening" and "Envoy sees it":

  • Keep-alive / connection reuse skewing concurrency. If a front-end proxy multiplexes many logical requests over few long-lived connections, Envoy's concurrent request count can look much lower than actual user-facing traffic volume.
  • Traffic bypassing ingress entirely. If something is calling the app directly via its FQDN in a way that skips the expected ingress path (for example, misconfigured internal DNS pointing somewhere unexpected), Envoy never observes those requests, so KEDA — which reads Envoy's metrics — has nothing to scale on.

Check the scale rule's configured threshold against realistic concurrency for your workload — a threshold of 50 concurrent requests means little if your traffic pattern rarely holds more than 5 requests in flight at once, however high total request volume is over time.

Common misdiagnosis: teams often assume "requests per second" from an external monitor is the same signal as the "concurrent requests" scale rule threshold. They're different measurements — a high request rate with short-lived requests can produce low concurrency, and low concurrency never crosses a threshold tuned for a different traffic shape.

04Root Cause

Container Apps' HTTP scale rules read concurrency as observed by the Envoy sidecar/ingress in front of each revision, not application-level request counters or external monitoring tools. When the configured threshold doesn't match the actual concurrency profile of real traffic — often because of connection reuse, short request durations, or a scale rule copied from a different workload's traffic pattern — the rule technically works correctly but never fires because the condition it's watching for genuinely isn't happening.

05Fix

  • Recalculate the threshold based on real concurrency, not request rate — use Log Analytics to look at actual in-flight request counts for your workload rather than assuming a default threshold fits.
  • Switch scale trigger type if HTTP concurrency is the wrong signal — for workloads with many short requests rather than sustained concurrency, a custom metric (CPU, queue length) may reflect load more accurately than HTTP concurrency.
  • Verify traffic actually routes through ingress as expected — confirm DNS and any upstream proxy configuration sends traffic to the app's public ingress endpoint rather than bypassing it.
  • Load test against the real threshold before trusting a scale rule in production — generate sustained concurrent load matching your configured threshold and confirm a new replica actually spins up.
Prevention tip: when setting an HTTP scale rule, base the threshold on measured concurrency from your own traffic (via Log Analytics), not a value copied from documentation examples or another team's app — traffic shape varies enough between workloads that a "reasonable default" often doesn't reflect reality.
