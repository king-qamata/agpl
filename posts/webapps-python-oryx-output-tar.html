Python on App Service: "Could Not Find output.tar.gz" After Deployment

Python Oryx 6 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

The app fails to start after what looked like a successful deployment, with an error referencing a missing output.tar.gz file. The deployment step in CI/CD reported success, which makes this confusing — the failure only shows up at container startup, not during deployment.

02Environment

  • Python application on App Service Linux using Oryx build (SCM_DO_BUILD_DURING_DEPLOYMENT=true)
  • An oryx-manifest.toml file is present, but output.tar.gz is not

03Diagnosis

The presence of oryx-manifest.toml without the accompanying output.tar.gz is the actual signal here: Oryx's Python images look for this compressed output at startup, and if the manifest exists but the archive doesn't, the build stage was started but never completed successfully — even though your pipeline's deployment step may have exited with a success code for a different reason (the upload succeeded; the build behind it did not).

  • Check whether the app was left in a mid-deployment state — stop the App Service, wait for any in-flight deployment operation to fully complete, then restart and check again before assuming this is a persistent build failure.
  • If it persists, go back to the actual Oryx build logs (not just the pipeline's summary output) and look for why the build stage failed or was interrupted.
Common misdiagnosis: because the pipeline reported success, teams sometimes assume the app itself is broken and start debugging application code. The actual failure is upstream, in the build stage — application code was never the problem here.

04Root Cause

Oryx's Python deployment model produces a compressed output.tar.gz as the final artifact of a successful build, alongside a manifest file describing what was built. If the build process is interrupted — for example, by a deployment operation overlapping with another one, or a build stage that errors out partway through — the manifest can be written before the failure occurs, while the final compressed artifact never gets created. The app then starts up expecting an artifact that doesn't exist.

05Fix

  • Let any in-flight deployment fully complete before redeploying — stop the app, wait, then check whether the issue resolves on its own once the interrupted operation finishes.
  • If it doesn't resolve, review the actual Oryx build log for the failure, not just your pipeline's top-level status — the build log will show where the process actually stopped.
  • Avoid triggering overlapping deployments to the same app — this is the same underlying Kudu concurrency constraint covered in this site's HTTP 409 post, and an interrupted build is one of the ways that conflict can manifest.
  • Redeploy cleanly once the cause is addressed — a fresh, uninterrupted deployment should regenerate both the manifest and the archive correctly.
Prevention tip: apply the same concurrency controls in your pipeline recommended for the HTTP 409 scenario — serializing deployments avoids this specific failure mode as well, since it stems from the same root cause of overlapping deployment operations.
