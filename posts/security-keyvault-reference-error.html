Key Vault Reference Shows "#REF!" in App Configuration

Key Vault Managed Identity 6 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

An application setting configured as a Key Vault reference (@Microsoft.KeyVault(...)) shows #REF! in the portal instead of resolving to the actual secret value, or resolving silently but the app fails at runtime trying to read what's effectively an empty or error string instead of the expected secret.

02Environment

  • App Service or Function App with an application setting using Key Vault reference syntax
  • Key Vault access configured via either RBAC or a legacy access policy
  • Recently added the reference, or recently changed the Key Vault's permission model

03Diagnosis

#REF! specifically means the platform tried to resolve the reference and failed — this is different from a setting that's simply missing or misspelled, which would show as literal text instead. Work through the resolution chain:

  • Confirm the app has a managed identity enabled — Key Vault references resolve using the app's own identity, not a shared credential.
  • Check the Key Vault's permission model — Key Vault supports both legacy access policies and Azure RBAC; confirm which one is active and that the app's identity has a grant under whichever model is actually enabled. A permission granted under the wrong model (e.g. an access policy on a vault now using RBAC) has no effect.
  • Verify the reference syntax itself — confirm the vault name, secret name, and optional version in the reference string exactly match what exists in the vault.
  • Check Key Vault's own network restrictions — if the vault has Private Endpoint-only access or firewall rules, confirm the app can actually reach it; this manifests the same as a permissions failure from the app's perspective.
Common misdiagnosis: because the syntax "looks right," teams sometimes assume the reference itself must be malformed and spend time tweaking the string. If the vault name and secret name are correct, the far more common cause is a permissions or network gap between the app's identity and the vault, not a syntax problem.

04Root Cause

Key Vault references are resolved server-side using the app's managed identity to fetch the secret at runtime — the app never sees a literal secret value in its configuration, only the reference. If that identity lacks a role or access policy grant on the vault (or under the wrong permission model relative to what the vault actually enforces), or can't reach the vault over the network, resolution fails and the platform surfaces that as #REF! rather than the resolved value.

05Fix

  • Enable a managed identity on the app if not already present.
  • Grant the correct permission for the vault's actual model: an RBAC role like Key Vault Secrets User if the vault uses Azure RBAC, or a get permission via an access policy if it's still on the legacy model.
  • If the vault restricts network access, ensure the app can reach it — via VNet integration and a Private Endpoint if the vault is locked to private networking, following the same pattern as the storage-focused Managed Identity posts on this site.
  • Re-save the app setting after fixing permissions — resolution sometimes needs a trigger to retry rather than resolving automatically the moment access is granted.
Prevention tip: when migrating a Key Vault from access policies to RBAC (or vice versa), audit every app identity that references secrets in that vault as part of the migration — a permission model switch silently breaks any reference relying on the old model's grants.
