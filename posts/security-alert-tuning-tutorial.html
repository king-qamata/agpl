Setting Up Azure Monitor Alerts That Don't Wake You Up for Nothing

Intermediate Azure Monitor 7 min read

A static threshold alert ("fire when CPU > 80%") is the easiest kind to set up and the easiest to get wrong — too tight and it pages on normal variance, too loose and it misses real problems. This walks through building alerts that account for a workload's actual behavior instead.

Before you start
  • An Azure resource emitting metrics you want to alert on
  • An Action Group already created, or willingness to create one during this walkthrough

  1. Start from a real metric baseline, not a guess

    Before setting any threshold, pull the actual metric history over a representative period (at least a week, ideally including a peak period) using the KQL fundamentals covered on this site, or the Metrics blade directly. A threshold set from documentation examples rather than your workload's real behavior is the root cause of most noisy alerts.

  2. Prefer dynamic thresholds over static ones where available

    For metrics with natural daily/weekly patterns (request volume, CPU tied to business hours), a dynamic threshold — which learns normal variance and alerts on deviation from it — handles predictable variance far better than any single static number.

    Conceptual difference
    Static:  alert if CPU > 80%
Dynamic: alert if CPU deviates significantly from
         its own learned pattern for this time of day/week

  3. Set an appropriate aggregation window

    A one-minute evaluation window on a naturally spiky metric fires constantly on noise; a window that's too long delays detection of genuine problems. Match the window to the metric's natural volatility — CPU often wants a longer window (5-15 min) than something like queue depth, which may need faster detection.

  4. Use severity levels deliberately

    Not every alert should page someone immediately. Reserve Sev 0/1 for genuinely actionable, time-sensitive conditions, and route lower-severity signals to a dashboard or a non-paging notification channel instead.

  5. Add alert processing rules for known maintenance windows

    Suppress or reroute alerts during planned deployments or maintenance, so a known, expected spike (like a deployment-triggered restart) doesn't generate a false page.

  6. Review fired alerts periodically and tune

    Treat alert thresholds as living configuration, not a one-time setup. Periodically review which alerts fired and whether each was genuinely actionable — an alert that fires often but never leads to action is a tuning problem, not a monitoring success.

Result: alert rules that reflect a workload's actual behavior rather than a generic threshold — the difference between alerts a team trusts and acts on versus ones that get silently muted after the third false page.
