Node.js Containers OOMKilled on Container Apps: Setting --max-old-space-size

Node.js OOMKilled 6 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A Node.js container gets killed under memory pressure — visible as an OOMKilled event in the container's system logs — during workloads that shouldn't be pushing memory usage anywhere near the container's configured limit, particularly on containers given a relatively small memory allocation.

02Environment

  • Node.js application in a container on Azure Container Apps
  • Container memory limit set to a value smaller than the host's total memory (typical for right-sized containers, e.g. 512Mi–1Gi)
  • No explicit V8 heap size flags set at container build or startup

03Diagnosis

Check what heap limit Node/V8 is actually using by default, and compare it against the container's memory limit.

bash — check V8's default old space size
node -e "console.log(require('v8').getHeapStatistics().heap_size_limit / 1024 / 1024, 'MB')"

If this number is significantly larger than the container's memory limit, that's the mismatch — V8's default heap sizing is based on available system memory as reported to the process, which in many container configurations reflects the host's total memory rather than the container's own cgroup-imposed limit.

Common misdiagnosis: an OOMKilled Node container is often investigated as an application memory leak first — profiling, heap snapshots, hunting for a growing object. If V8's own reported heap limit is already larger than the container's memory budget, the container can be killed under normal, non-leaking memory usage simply because V8 believes it has more room than it actually does.

04Root Cause

V8 sizes its default heap limit based on the system memory it detects, and depending on the Node.js version and container runtime configuration, that detection may not correctly reflect the container's actual cgroup memory limit — instead reflecting the underlying host's total memory. This means V8 can allow the heap to grow toward a ceiling that's larger than what the container is actually permitted to use, and the container runtime kills the process once total memory usage (heap plus everything else) exceeds the real limit, regardless of what V8 itself believes its ceiling is.

05Fix

  • Set --max-old-space-size explicitly, sized conservatively below the container's memory limit to leave room for non-heap memory (V8's own overhead, native modules, buffers).
  • Account for memory outside the V8 heap — Buffers, native addon memory, and the Node.js runtime itself all consume container memory that --max-old-space-size doesn't cover; don't set the flag to a value close to the full container limit.
  • Use a recent Node.js LTS version where container memory detection has generally improved, and verify behavior specifically on your chosen base image rather than assuming it's correct by default.
  • Load test at the target container memory limit to confirm the chosen heap size setting actually prevents OOMKilled under realistic load, the same verification step used in the capacity planning tutorial on this site.
Prevention tip: set --max-old-space-size explicitly as a standard part of any Node.js container's startup configuration, rather than relying on V8's automatic detection — treat it as required configuration for containerized Node, not an optional tuning knob.
