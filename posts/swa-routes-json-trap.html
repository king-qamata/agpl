SWA Build Passes, Site 404s: the routes.json Trap

GitHub Actions staticwebapp.config.json 6 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

The GitHub Actions workflow for a Static Web App completes successfully — green checkmark, no build errors — but visiting the deployed site returns a 404, or specific client-side routes (like a React Router path) 404 on direct navigation or refresh, even though clicking through the app from the homepage works fine.

02Environment

  • Azure Static Web Apps with a single-page app framework (React, Vue, Angular) using client-side routing
  • Deployment via the Azure Static Web Apps GitHub Actions workflow
  • Build output located in a non-default folder, or a staticwebapp.config.json that's missing, misplaced, or has an incorrect fallback route

03Diagnosis

Separate the two failure modes, because they have different causes:

  • The whole site 404s: check the workflow YAML's app_location and output_location values against where your build tool actually places its output. A mismatch means SWA is looking for files in the wrong folder even though the build itself succeeded.
  • Only deep-linked or refreshed routes 404: this is a client-side routing fallback issue, not a build issue. The static file host doesn't know that /dashboard/settings should serve index.html and let your JS router take over — it looks for a literal file at that path and fails.

Check whether staticwebapp.config.json exists in your app_location folder and gets included in the deployed output — a common mistake is placing it in the repo root when the build tool's output folder is what actually gets deployed, leaving the config file behind.

Common misdiagnosis: because the homepage and in-app navigation work fine, teams often assume the site is fully functional and only discover the issue when a user bookmarks or refreshes a deep link — by which point it looks like a "random" bug rather than a routing configuration gap.

04Root Cause

Static Web Apps serves files directly by path unless told otherwise. Single-page apps rely on the browser's JS router to handle paths client-side, which only works if the server falls back to serving index.html for unmatched routes. Without a correctly placed staticwebapp.config.json defining that fallback (via the navigationFallback setting), any direct request to a client-side route 404s at the server before your app's JavaScript ever runs.

05Fix

  • Place the config correctly: put staticwebapp.config.json inside the folder your build tool outputs to production files (e.g. dist or build), or configure your build to copy it there — not just in the repo root, unless that's also your app_location.
  • Add a navigation fallback: configure navigationFallback.rewrite to point to /index.html so unmatched routes fall back to your SPA entry point instead of 404ing.
  • Exclude real static assets from the fallback: use navigationFallback.exclude so requests for actual files (images, JS bundles, API routes under /api/*) aren't incorrectly rewritten to index.html.
  • Double-check build output paths: confirm app_location and output_location in the workflow YAML match your framework's actual build output folder (these differ between Create React App, Vite, Next.js static export, etc.).
Prevention tip: add a post-deploy smoke test to your CI pipeline that curls a known deep-linked route (not just the homepage) — a green build doesn't confirm routing works, only that the build step itself succeeded.
