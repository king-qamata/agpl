Java on Container Apps: Setting JVM Heap Limits to Match Container Memory

Java OOMKilled 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A Java container gets killed and restarted with an out-of-memory condition, even though the application's actual working set looks well within the container's configured memory limit — for example, a container limited to 1Gi getting killed when the app itself doesn't appear to be using anywhere near that much.

02Environment

  • Java application in a container on Azure Container Apps
  • Container memory request/limit set explicitly (e.g. 1Gi)
  • Base image is a general-purpose JDK image, or JVM flags weren't set explicitly for container awareness

03Diagnosis

Check what heap size the JVM actually chose at startup versus what you'd expect given the container's memory limit — this is visible via a startup flag or by inspecting the running JVM.

bash — check the JVM's chosen max heap
java -XX:+PrintFlagsFinal -version | grep -i maxheapsize

If the reported max heap is much larger than a value that would fit comfortably within the container's memory limit (accounting for non-heap JVM overhead — thread stacks, metaspace, direct buffers), that's the signal: the JVM sized its heap against a memory figure that doesn't match the actual container constraint.

Common misdiagnosis: this gets treated as a memory leak in application code, and teams start profiling heap usage or hunting for leaks. If the container is killed well before the application's own heap usage looks concerning, the JVM's heap sizing relative to the container limit — not a leak — is the more likely first thing to check.

04Root Cause

Modern JDKs (10+) are container-aware by default and size the heap based on the container's cgroup memory limit rather than the host's total memory — but this depends on the JVM correctly detecting that limit, and on the container's total memory budget correctly accounting for everything outside the heap (metaspace, thread stacks, JIT compiled code cache, direct byte buffers). A heap sized as a naive fraction of the container's total memory limit, without headroom for that non-heap overhead, means the JVM's actual total memory footprint exceeds the container's limit even though the heap itself is "within bounds" — and the container runtime kills the process for exceeding its cgroup limit.

05Fix

  • Set an explicit, conservative max heap rather than relying entirely on the JVM's automatic sizing — -XX:MaxRAMPercentage set to something like 50-70% (not close to 100%) leaves headroom for non-heap memory.
  • Account for non-heap memory explicitly — metaspace, thread stacks (multiplied by thread count), and direct buffers all consume container memory outside the Java heap; size the container's memory limit with this overhead in mind, not just the intended heap size.
  • Verify container-awareness is actually active — confirm the specific base image and JDK version correctly detects cgroup limits; some minimal or older images have had inconsistent behavior here.
  • Load test at the target container memory limit before shipping, watching for OOMKilled events specifically, not just apparent heap usage from inside the JVM.
Prevention tip: for the Container Apps capacity planning exercise covered elsewhere on this site, treat JVM memory configuration as part of that sizing exercise specifically for Java workloads — the container memory limit and the JVM's own flags need to be reasoned about together, not set independently.
