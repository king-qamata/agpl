KQL Fundamentals: the Six Operators You'll Use in Every Investigation

Beginner Azure Monitor 8 min read

Every troubleshooting post on this site leans on Kusto Query Language (KQL) at some point. Rather than explain the syntax fresh each time, this covers the small set of operators that cover the vast majority of real investigations — once these are second nature, you can follow (and write) nearly every query on this site.

Before you start
  • Access to a Log Analytics workspace or Application Insights resource with some data in it
  • The Logs blade open in the Azure Portal

  1. where — filter rows

    The workhorse operator. Every query starts with a table name and narrows down from there, almost always beginning with a time filter to avoid scanning more data than necessary.

    KQL
    requests
| where timestamp > ago(1h)
| where success == false

  2. summarize — aggregate rows into stats

    Turns raw rows into counts, averages, or percentiles grouped by whatever dimension matters — commonly time buckets, but also route name, status code, or region.

    KQL
    requests
| where timestamp > ago(6h)
| summarize count(), avg(duration), percentile(duration, 95) by bin(timestamp, 15m)

  3. extend — add a computed column

    Useful for deriving a new field without changing the underlying data — like flagging rows as "cold" or "warm" based on a threshold, which several posts on this site use directly.

    KQL
    requests
| extend isSlow = iff(duration > 3000, "slow", "normal")

  4. order by — sort results

    Almost always paired with desc to see the most recent or most extreme values first — the slowest requests, the most recent errors, the highest CPU samples.

    KQL
    requests
| where timestamp > ago(1h)
| order by duration desc

  5. join — combine data from two tables

    Correlates data across tables that share a common field — for example, matching request telemetry against infrastructure metrics like CPU, as used in the App Service high-CPU investigation on this site.

    KQL
    requests
| where timestamp > ago(2h)
| join kind=inner (
    AzureMetrics
    | where MetricName == "CpuPercentage"
) on TimeGenerated

  6. render — visualize inline

    Renders the result as a chart directly in the Logs blade — useful for spotting a pattern (a spike, a bimodal distribution) before writing a more targeted filtering query.

    KQL
    requests
| where timestamp > ago(24h)
| summarize count() by bin(timestamp, 1h)
| render timechart
Result: with just these six operators — where, summarize, extend, order by, join, and render — you can reconstruct nearly every diagnostic query used across this site's troubleshooting posts. Everything else in KQL is refinement on top of this base.
