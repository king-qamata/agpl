Deploying Next.js to Static Web Apps: Static Export vs Hybrid Rendering Limits

Next.js SSR / ISR 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A Next.js app deploys successfully to Static Web Apps, but specific pages or features don't work as expected in production — API routes return 404, pages that should update per-request show stale content, or dynamic routes relying on server-side data fetching render empty. The same app works fully in local development.

02Environment

  • Next.js app using API routes, Server-Side Rendering (SSR), or Incremental Static Regeneration (ISR)
  • Deployed to Static Web Apps, which is fundamentally a static hosting platform plus a separate managed Functions API

03Diagnosis

Check which specific Next.js features are in use and cross-reference against what SWA's build preset actually supports. Static Web Apps' Next.js support is built around static export — pages that can be fully pre-rendered at build time. Features that require a persistent Node.js server process at request time (traditional SSR, ISR with revalidation, API routes as Next.js defines them) don't have an equivalent in a purely static deployment, even though the Next.js build itself may complete without error.

  • Confirm whether the SWA build configuration is using static export mode, and whether your app's routes are compatible with that (no getServerSideProps, no revalidating ISR).
  • Check whether "API routes" in your app were expected to run as Next.js API routes specifically, versus being redirected to work as SWA's own linked Azure Functions API — these are different mechanisms with different code.
Common misdiagnosis: a successful build is often taken as confirmation the deployment will work fully in production. Static export can succeed at build time while silently dropping server-dependent behavior — the build doesn't fail, the feature just doesn't function the way it did with a real Node.js server behind it.

04Root Cause

Static Web Apps' core hosting model serves pre-built static files plus a separate Functions-based API — it isn't a general-purpose Node.js server host. Next.js features that assume a persistent server process handling each request (SSR, ISR revalidation, native API routes) don't map onto that model directly. Static export mode works because it moves all rendering to build time, but that means anything requiring per-request server logic has to be redesigned around SWA's actual architecture, not just deployed as-is.

05Fix

  • Convert server-side data fetching to static generation where possible — getStaticProps instead of getServerSideProps, accepting that data is fixed at build time rather than live per request.
  • Move genuine API logic to SWA's linked Functions API explicitly, rather than relying on Next.js's own API routes convention, since that's the mechanism SWA actually supports for backend logic.
  • Rebuild and redeploy on a schedule or on content change as a substitute for ISR if content needs to refresh periodically — this trades true revalidation for a build-triggered refresh instead.
  • If the app genuinely needs full SSR, reconsider whether SWA is the right host — Web App for Containers or a Node.js-capable App Service plan supports a real Next.js server process directly, which may be a better fit than working around SWA's static model.
Prevention tip: decide on static export versus a server-hosting platform before building out Next.js-specific server features — retrofitting an SSR-heavy app onto SWA's static model after the fact is significantly more work than choosing the right hosting target from the start.
