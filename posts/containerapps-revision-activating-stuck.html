Revisions Stuck in "Activating" State on Container Apps

Revisions Health Probes 6 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A revision reaches Activating status and stays there indefinitely, never transitioning to Running. This is a distinct failure point from a revision stuck in Provisioning (covered in the Dapr sidecar checklist on this site) — by the time a revision reaches Activating, the container image itself has already been pulled and the container has started.

02Environment

  • Azure Container Apps, revision recently created or updated
  • Container starts successfully (visible in console logs) but the revision doesn't progress to Running
  • Custom liveness or readiness probes may be configured

03Diagnosis

Activating specifically means the container process has started but hasn't yet passed the checks Container Apps uses to decide it's ready to receive traffic. Unlike a Provisioning-stuck revision (usually a Dapr or environment-level issue), an Activating-stuck revision points at the container's own health signaling:

  • Check configured liveness/readiness probes — if a custom probe path is set, confirm the application actually serves a successful response on that exact path and port.
  • Check whether the app takes longer to become ready than the probe's failure threshold allows — a probe with a short timeout and low failure threshold can mark an otherwise-healthy but slow-starting app as failed before it ever gets a chance to respond.
  • Check console logs for the container (via the KQL primer on this site) for errors occurring after startup but before the app would normally start serving — a crash loop after initial start looks like "stuck Activating" from the platform's perspective.
Common misdiagnosis: because the container clearly starts (it shows up in logs, the process is running), teams sometimes assume the platform itself is stuck. If a probe is configured and never returns success, or the app crashes shortly after starting, the platform is behaving correctly — it's accurately reporting that the container never became healthy.

04Root Cause

Container Apps won't mark a revision Running until the container demonstrates it's actually ready to serve traffic, via either a default TCP-based check or a custom HTTP liveness/readiness probe if configured. A probe pointed at the wrong path or port, a probe timeout too aggressive for the app's real startup time, or an application that crashes shortly after starting (rather than failing immediately) all leave the revision stuck exactly at this stage.

05Fix

  • Verify probe configuration matches reality — confirm the path, port, and expected response code in the probe definition against what the application actually serves.
  • Loosen probe timing if startup is legitimately slow — increase the initial delay and failure threshold to give the app a realistic window to become ready before being marked unhealthy.
  • Fix any post-startup crash surfaced in console logs — this is a normal application bug at that point, not a Container Apps platform issue, and should be debugged the same as any other runtime crash.
  • Test probes locally first where possible — curl the exact probe path against a locally running container to confirm it returns the expected response before deploying.
Prevention tip: when adding a custom health probe to a Container App, deliberately test both the success and slow-startup cases — a probe that's never been tested against a genuinely slow cold start will often turn out to be misconfigured exactly when it matters most, during a real deployment under load.
