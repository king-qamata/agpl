Diagnosing Memory Leaks in Windows Web Apps with a Memory Dump

Windows App Service WinDbg 8 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

Private memory usage for the worker process climbs steadily over hours or days rather than settling into a stable pattern. Eventually the app either hits the plan's memory limit and gets recycled, or starts throwing OutOfMemoryException. Restarting the app "fixes" it temporarily — a strong signal you're dealing with a leak rather than a single bad request.

02Environment

  • Windows App Service Plan running ASP.NET or ASP.NET Core
  • Memory usage graph in the portal shows a steady upward slope, not spikes tied to traffic
  • Issue reproduces gradually over real production traffic, making it hard to catch in a quick local test

03Diagnosis

A memory graph alone tells you that memory is leaking, not what is holding onto it — for that you need a memory dump captured while usage is elevated, ideally two dumps taken some time apart so you can compare growth.

  • In Kudu, go to Diagnose and solve problems → Diagnostic Tools, or use Process Explorer directly, and collect a memory dump of the w3wp.exe process while memory is elevated but before the app is recycled.
  • Take a second dump 15–30 minutes later if possible — comparing object counts between the two is far more informative than a single snapshot.
  • Open the dump in a tool that can inspect managed heap contents (WinDbg with SOS, or a managed memory profiler). Look at object counts by type, sorted by total retained size, not just instance count — a million small objects and ten enormous ones can both be the culprit.
Common misdiagnosis: a rising memory graph is often blamed on "GC not running" — but the .NET garbage collector generally does its job correctly. The far more common cause is something in application code holding a live reference to objects that should have been eligible for collection, which the GC correctly leaves alone.

04Root Cause

In managed applications, memory leaks are almost always reference leaks, not GC failures. The most frequent patterns:

  • Event handler subscriptions that are never unsubscribed — the subscriber keeps the publisher (or vice versa) alive indefinitely.
  • Static collections that only ever grow — a cache or list with no eviction policy, accumulating one entry per request.
  • Captured closures in long-lived callbacks — a lambda capturing a large object graph, registered against something with app-lifetime scope.
  • Disposable objects not disposed — particularly unmanaged resources wrapped in .NET types (streams, HTTP clients created per-request instead of reused).

05Fix

  • Identify the growing type from the dump comparison, then trace its GC roots (what's still referencing it) — this points directly at the offending code path.
  • Unsubscribe event handlers in the appropriate lifecycle method (Dispose, or equivalent) for anything with app-lifetime scope subscribing to shorter-lived events.
  • Add eviction to caches — use a bounded cache (size or time-based eviction) instead of an unbounded static dictionary or list.
  • Reuse expensive clients — for example, use a single shared HttpClient (or IHttpClientFactory) instead of creating one per request.
  • Verify with a follow-up dump after the fix — confirm the previously-growing type count now stabilizes under the same traffic pattern.
Prevention tip: add a memory-usage alert well below your plan's hard limit (e.g. 75%) so you get paged while you still have time to capture a diagnostic dump — once the app is actively being recycled by the platform, you lose the window to catch it in a useful state.
