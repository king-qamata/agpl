Troubleshooting CORS Errors Between WordPress, Azure CDN/Front Door, and Blob Storage

WordPress on Linux App Service Azure CDN / Front Door 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

Fonts, images, or other static assets offloaded to Blob Storage and fronted by Azure CDN or Front Door fail to load in the browser. The browser console shows a CORS error such as "No 'Access-Control-Allow-Origin' header is present on the requested resource," even though the assets load fine when accessed directly by URL.

02Environment

  • WordPress hosted on Azure App Service Linux
  • Media/static assets offloaded to Azure Blob Storage for performance
  • Azure CDN or Azure Front Door sitting in front of Blob Storage and/or the App Service origin
  • WordPress theme or plugin loading fonts or assets cross-origin (e.g. from a CDN subdomain different from the main site domain)

03Diagnosis

Open browser dev tools and check the failing request's response headers, not just the console error. The key thing to confirm is whether Access-Control-Allow-Origin is present at all, and if so, whether it matches the requesting origin exactly.

  • Test the asset URL directly in a new tab — if it loads fine there but fails when loaded by the page's JavaScript or CSS, that confirms it's specifically a cross-origin browser restriction, not a broken link.
  • Check whether CORS rules are configured on the Blob Storage account itself (Storage account → Resource sharing (CORS)) — this is a separate setting from anything in WordPress or App Service.
  • If a CDN or Front Door sits in front of Blob Storage, confirm it isn't caching a stale response that was captured before CORS headers were added, or stripping headers during caching.
Common misdiagnosis: teams often add CORS headers at the WordPress/App Service level (e.g. via .htaccess or a plugin) when the request never actually reaches App Service — it's served entirely from Blob Storage or the CDN edge, so the fix has to happen at that layer instead.

04Root Cause

CORS headers must be set at the layer that actually serves the response to the browser. When assets are offloaded to Blob Storage and served via CDN, that means the Storage account's CORS rules (and possibly CDN caching behavior) — not WordPress — control whether the browser accepts the cross-origin response. A missing or overly narrow CORS rule on the Storage account, or a cached response from before CORS was configured, are the two most common causes.

05Fix

  • Configure Storage account CORS: in the Storage account, add a CORS rule permitting the origins that need to load the assets (your WordPress domain, and any CDN endpoint domain in use), with the HTTP methods actually used (typically GET, HEAD).
  • Purge the CDN cache: after updating CORS rules, purge cached responses for the affected paths so the CDN re-fetches from origin with the new headers rather than serving a stale cached copy.
  • Be specific with allowed origins: avoid wildcarding * for allowed origins if the assets include anything sensitive; list the actual domains that need access.
  • Check Front Door rules separately: if using Front Door, confirm it isn't rewriting or stripping the Origin or CORS response headers in a rules engine configuration.
Prevention tip: when first setting up asset offloading to Blob Storage or CDN, add the CORS rule as part of the initial setup checklist rather than after the fact — it's easy to forget because the assets "work" (load directly) right up until a browser enforces cross-origin restrictions.
