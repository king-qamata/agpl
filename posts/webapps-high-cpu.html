High CPU on App Service: Reading Process Explorer Correctly

Windows App Service Plan Kudu 9 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

CPU utilization on the App Service Plan sits at 80–100% for sustained periods during business hours. Page loads slow down or start timing out. Scaling out to more instances helps temporarily, but each new instance also climbs to high CPU within minutes — which is the tell that this isn't a capacity problem, it's a per-request efficiency problem.

02Environment

  • Windows App Service Plan (commonly P1v3 or similar)
  • ASP.NET Core application
  • Autoscale rule configured on CPU percentage
  • Traffic is steady rather than bursty — CPU climbs gradually with load, not in a single spike

03Diagnosis

Resist the urge to just scale up. Go to the Kudu console at https://<your-app>.scm.azurewebsites.net and open Process Explorer. This shows every process under the app's worker, including each w3wp.exe and its live CPU percentage — this is the fastest way to confirm the app's own code is the consumer, not something external like antivirus scanning or a sidecar process.

Once you've confirmed the worker process itself is hot, capture evidence rather than guessing at the cause:

  • Use Diagnose and solve problems → Diagnostic Tools → Collect a memory dump while CPU is elevated, or trigger a CPU profile directly from Process Explorer if available on your plan tier.
  • Download the dump and inspect thread stacks — look for a large number of threads blocked in the same call path, which points to lock contention or thread pool starvation rather than one runaway computation.
Kusto Query Language (KQL) — correlate CPU with request volume
AppServiceHTTPLogs
| where TimeGenerated > ago(2h)
| summarize RequestCount=count(), AvgDuration=avg(TimeTaken) by bin(TimeGenerated, 5m)
| join kind=inner (
    AzureMetrics
    | where MetricName == "CpuPercentage"
    | summarize AvgCpu=avg(Average) by bin(TimeGenerated, 5m)
) on TimeGenerated
| order by TimeGenerated desc
Common misdiagnosis: teams often jump straight to "we need a bigger SKU." That masks the symptom for a while, but if the underlying cause is thread pool starvation or an O(n²) code path, CPU will climb right back up as traffic grows into the new headroom.

04Root Cause

In practice, sustained high CPU under steady load traces back to one of a small set of causes:

  • Thread pool starvation: synchronous blocking calls (.Result, .Wait()) on async code tie up worker threads, so the runtime spins up more threads than it needs and burns CPU on context switching.
  • Inefficient hot-path code: unindexed LINQ over large in-memory collections, or a regex re-compiled on every request instead of cached, both scale badly with traffic.
  • Missing caching: expensive computation or serialization repeated per-request when the result rarely changes.
  • GC pressure: excessive short-lived allocations force frequent garbage collection, which itself consumes CPU.

05Fix

  • Thread starvation: convert blocking calls to async/await all the way up the call stack. Avoid mixing sync-over-async.
  • Hot-path inefficiency: profile with the captured dump or a local profiler to find the actual method consuming CPU, then optimize or cache its output.
  • Caching: add response caching or an Azure Cache for Redis layer in front of expensive, repeatable computation.
  • GC pressure: reduce large object allocations in hot paths; consider Server GC mode for App Service if not already enabled.
  • Short-term mitigation only: scaling up or out buys time while you root-cause — it is not the fix on its own.
Prevention tip: add a standing alert on CPU percentage sustained over 80% for more than 10 minutes, separate from your autoscale trigger, so you get notified even when autoscale successfully hides the symptom from users.
