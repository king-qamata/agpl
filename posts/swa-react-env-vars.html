Environment Variables Not Working in React on Static Web Apps: the Build-Time Trap

React Vite / CRA 6 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

An application setting is added or changed in the Static Web App's Configuration blade — an API URL, a feature flag — but the deployed React app keeps using the old value, or shows the variable as undefined entirely. Restarting or re-visiting the site doesn't help.

02Environment

  • React app built with Create React App or Vite, deployed via the Static Web Apps GitHub Actions workflow
  • Environment variable referenced in code as process.env.REACT_APP_* (CRA) or import.meta.env.VITE_* (Vite)
  • Value set as an Application Setting in the SWA resource's Configuration

03Diagnosis

Static Web Apps' Application Settings are runtime configuration for the managed Functions API backend — they are not automatically injected into the static frontend bundle. A React app is fully built and bundled during the CI/CD workflow, before it ever reaches Azure, so anything the frontend reads via process.env or import.meta.env has to already be present at that build step.

  • Check whether the variable is prefixed correctly for your build tool — CRA only exposes variables prefixed REACT_APP_, Vite only exposes ones prefixed VITE_; anything else is silently excluded from the bundle.
  • Check where the value is actually being set — an SWA Application Setting is invisible to the frontend build unless it's also passed into the GitHub Actions build step as a build-time environment variable.
Common misdiagnosis: because Application Settings work as expected for the linked Functions API, it's easy to assume the same mechanism applies to the static frontend. The frontend and the API have fundamentally different configuration models — one is compiled in ahead of time, the other reads environment variables at request time.

04Root Cause

CRA and Vite both replace environment variable references with their literal values at build time — this is a static text substitution baked into the JavaScript bundle, not a runtime lookup. Once built, there's no code path left that reads an actual environment variable; the value is just a string in the compiled bundle. Changing an Azure Application Setting after the fact has no effect because the build already happened and the resulting static files don't reference the environment at all.

05Fix

  • Pass the value into the build step in your GitHub Actions workflow YAML as an environment variable available during the npm run build step, sourced from a GitHub Actions secret or variable rather than an Azure Application Setting.
  • Rebuild and redeploy any time the value needs to change — there's no way to update a build-time-baked value without re-running the build.
  • If the value genuinely needs to change without a rebuild (e.g. differs per environment without redeploying), fetch it at runtime from the linked API instead of baking it into the frontend bundle — the API layer can read Application Settings normally since it runs as an actual server-side process.
  • Double-check the variable prefix matches your build tool's requirement exactly — a missing REACT_APP_/VITE_ prefix is a common and easy-to-miss mistake distinct from the build-time/runtime issue itself.
Prevention tip: document clearly, for anyone working on the frontend, which config values are build-time (frontend, baked into the bundle) versus runtime (API, read from Application Settings) — this distinction isn't obvious from the SWA portal UI alone, and it's the single most common source of "my settings aren't working" confusion on this platform.
