Setting Up Application Insights and Writing Your First KQL Query

Beginner Application Insights 7 min read

Every troubleshooting post on this site leans on Application Insights and Kusto Query Language (KQL) to find root cause instead of guessing. If you haven't set this up yet, this walks through it end to end — from enabling the resource to running a real query against your Function App's traffic.

Before you start
  • An existing Function App or Web App in Azure
  • Contributor access on the resource group
  • Access to the Azure Portal

  1. Create or link an Application Insights resource

    In the Azure Portal, open your Function App, go to Settings → Application Insights, and either enable a new resource in the same region or link an existing one. This is the single most important step — without it, none of the later diagnosis posts on this site are possible for your app.

  2. Confirm telemetry is flowing

    Send a few test requests to your app, then open the Application Insights resource and check the Live Metrics blade. You should see request counts and server response times updating within a few seconds. If nothing appears after a minute, double check the APPLICATIONINSIGHTS_CONNECTION_STRING app setting is present and correctly formatted.

  3. Open the Logs (Kusto) blade

    From the Application Insights resource, select Logs in the left nav. This opens the Kusto query editor scoped to your telemetry data. Close any "example queries" popup — you'll write your own in the next step.

  4. Run your first query: recent request volume

    Paste the query below and run it. This returns request count and average duration bucketed by 15-minute windows over the last 6 hours — a good first sanity check that data is arriving as expected.

    KQL — request volume, last 6 hours
    requests
| where timestamp > ago(6h)
| summarize RequestCount=count(), AvgDurationMs=avg(duration) by bin(timestamp, 15m)
| order by timestamp desc

  5. Filter to a specific function or route

    Add a where clause on name to scope the query to one endpoint — this is the pattern you'll reuse in nearly every troubleshooting query on this site.

    KQL — scoped to one function
    requests
| where timestamp > ago(6h)
| where name == "GET /api/YourFunction"
| summarize count(), avg(duration), percentile(duration, 95) by bin(timestamp, 15m)

  6. Pin the query for reuse

    Click Pin to dashboard in the query editor toolbar. Over time, pin your most-used diagnostic queries (p95 latency, failed request rate, exception count) so a health check takes one glance instead of retyping KQL during an active incident.

Result: you now have telemetry flowing and a working Logs query. The troubleshooting posts on this site build directly on this setup — for example, the cold start diagnosis post reuses the same query pattern with a duration threshold added.
