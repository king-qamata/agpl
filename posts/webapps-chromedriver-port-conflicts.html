ChromeDriver Port Conflicts on App Service: Migrating from a Persistent Service to On-Demand Instances

PHP ChromeDriver 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A PHP script driving headless Chrome via a shared ChromeDriver service (managed by Supervisor, listening on a fixed port like 9515) works reliably when run one at a time, but starts throwing connection errors, session conflicts, or unexplained hangs as soon as more than one script runs concurrently.

02Environment

  • PHP on App Service Linux, custom container with Chrome/ChromeDriver installed
  • ChromeDriver running as a single, Supervisor-managed persistent service on a fixed port
  • Multiple requests or scheduled scripts potentially overlapping in execution

03Diagnosis

Confirm this is a concurrency issue specifically by checking whether failures correlate with overlapping script executions rather than any single script's own logic. A single ChromeDriver process handles one WebDriver session cleanly, but a second concurrent request either queues behind the first (causing apparent hangs) or, depending on how sessions are managed, can cross-contaminate state between unrelated automation runs.

  • Check process listings during a failure window for multiple PHP scripts attempting to talk to the same ChromeDriver port simultaneously.
  • Correlate failure timestamps against your scheduling/triggering mechanism — cron jobs, queued requests, or concurrent HTTP calls that happen to overlap.
Common misdiagnosis: intermittent failures under load are often chased with timeout increases or retry logic layered on top of the shared-service architecture. This treats the symptom rather than the cause — a shared, stateful ChromeDriver service fundamentally isn't designed for concurrent unrelated sessions, and no amount of retrying fixes that.

04Root Cause

A single ChromeDriver instance on a fixed port serves one browser session cleanly, but concurrent scripts sharing that same instance either collide on the port, contend for the same underlying browser session, or interfere with each other's Chrome profile state. This architecture works by coincidence at low volume — the moment two automation runs genuinely overlap in time, the shared service becomes a bottleneck and a source of cross-request interference.

05Fix

Move from one shared, persistent ChromeDriver service to on-demand, isolated instances — one ChromeDriver process per script execution, on a random port, with its own Chrome profile directory. This is the architecture covered in the PHP Chrome automation tutorial on this site.

  • Start ChromeDriver per-script via ChromeDriver::start() rather than connecting to a shared, pre-running instance.
  • Use a unique profile directory per instance (e.g. /tmp/chrome-profiles/profile-{uniqid}) so concurrent sessions never share Chrome's own state.
  • Remove the Supervisor-managed persistent ChromeDriver service entirely once migrated — leaving it running alongside the new pattern reintroduces the exact port conflict this fix removes.
  • Add cleanup for orphaned profile directories on a schedule, since a script that crashes before cleanup can leave a stale profile directory behind.
Prevention tip: if a new automation workload is being designed, default to the on-demand instance pattern from the start rather than a shared service — the shared-service approach's problems only appear under concurrency, which means they're easy to miss during initial development and testing at low volume.
