Reacting to Cosmos DB Changes with Change Feed and Functions

Intermediate Cosmos DB 7 min read

The Cosmos DB trigger lets a function react to document inserts and updates as they happen, backed by Cosmos DB's change feed. It's a different binding shape from Blob or Queue triggers — this walks through the specific pieces that trip people up: the lease container and partition key considerations.

Before you start
  • An existing Cosmos DB account and container with data you want to react to
  • Azure Functions Core Tools

  1. Create a lease container

    The Cosmos DB trigger requires a second container — conventionally named leases — used internally to track which changes have already been processed. Create it in the same database, and let the trigger create it automatically on first run if you prefer, via the CreateLeaseContainerIfNotExists setting.

  2. Scaffold the trigger function

    function.json
    {
  "bindings": [
    {
      "name": "documents",
      "type": "cosmosDBTrigger",
      "direction": "in",
      "connectionStringSetting": "CosmosDBConnection",
      "databaseName": "mydatabase",
      "collectionName": "orders",
      "leaseCollectionName": "leases",
      "createLeaseCollectionIfNotExists": true
    }
  ]
}

  3. Understand what the trigger actually delivers

    The change feed delivers inserts and updates — not deletes, which don't appear in the change feed by default. If you need to react to deletions, that requires a different pattern (e.g. a soft-delete flag your application sets, which then shows up as an update).

  4. Process the batch of changed documents

    The trigger delivers changes as a batch (a list), not one document per invocation — iterate over the batch in your handler rather than assuming a single document.

    C# — processing a batch
    [Function("ProcessOrderChanges")]
public void Run([CosmosDBTrigger(
    databaseName: "mydatabase",
    containerName: "orders",
    Connection = "CosmosDBConnection",
    LeaseContainerName = "leases",
    CreateLeaseContainerIfNotExists = true)]
    IReadOnlyList<MyDocument> changedDocuments)
{
    foreach (var doc in changedDocuments)
    {
        // handle each changed document
    }
}

  5. Consider partition key distribution

    The change feed processor scales by distributing partition key ranges across function instances — a poorly chosen partition key with heavily skewed distribution limits how well this scales, the same underlying concern as designing Cosmos DB partitioning generally, just now visible through trigger throughput.

  6. Verify with a test write

    Insert or update a document directly against the source container and confirm the function fires within a few seconds, processing the correct document content.

Result: a function reacting to Cosmos DB changes in near real time, with the lease container correctly tracking processing state — the detail most commonly missed when this trigger "doesn't seem to fire" on a first attempt.
