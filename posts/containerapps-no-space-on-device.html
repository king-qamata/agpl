"No Space on Device" Errors on Container Apps

Ephemeral Storage Container Apps 6 min read

02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

An application inside a Container App fails a disk write operation with an error like "no space left on device," despite the workload not appearing to handle unusually large amounts of data. This often surfaces during deployment, logging, or any operation writing temporary files to the container's local filesystem.

02Environment

  • Azure Container Apps, any plan
  • Application writing to local disk — temp files, local caching, log files, or build artifacts during a container build step
  • No explicit volume mount configured for the affected path

03Diagnosis

Container Apps provides a limited amount of ephemeral local storage per replica by default — this is separate from, and much smaller than, whatever disk capacity the underlying host has. An app that assumes it has substantial local disk space to work with (writing large temp files, aggressive local caching, verbose logging without rotation) can exhaust this quickly even though the workload doesn't seem unusually large in absolute terms.

  • Check what's actually writing to disk — application logs, temp file generation, or a caching layer are the most common culprits.
  • Confirm whether logs are rotated or bounded — unbounded log growth inside the container is a frequent, easy-to-miss cause.
  • Check if the workload was recently changed to process larger files or datasets than before, without a corresponding change to how (or whether) it uses persistent storage instead of local disk.
Common misdiagnosis: teams sometimes assume this reflects a genuine platform capacity issue and try to work around it with retries or by reducing workload size marginally. The actual constraint is the ephemeral storage allocation specific to Container Apps, not the underlying infrastructure's real capacity — the fix is architectural (external storage) rather than incremental (write less).

04Root Cause

Each Container Apps replica gets ephemeral local storage sized for typical container workloads — enough for normal application operation, but not intended as a substitute for genuine persistent or bulk storage. Applications ported from an environment with generous local disk (a VM, a container host with large volumes) can hit this ceiling unexpectedly if they weren't designed with ephemeral storage constraints in mind.

05Fix

  • Move bulk or persistent data to Azure Files or Blob Storage rather than the container's local filesystem — mount Azure Files as a volume for anything that needs to persist or exceeds ephemeral storage limits.
  • Bound and rotate application logs rather than letting them grow unbounded inside the container — ship logs to Log Analytics instead of relying on local log files for anything beyond transient debugging.
  • Stream large data rather than buffering it fully to local disk where the workload allows it — processing data in chunks avoids needing local storage proportional to the full dataset size.
  • Clean up temp files explicitly within long-running processes rather than assuming the container's ephemeral storage will be reset frequently enough to not matter.
Prevention tip: when migrating a workload to Container Apps from a VM or a hosting model with more generous local disk, explicitly audit what it writes to local disk and how much — this is exactly the kind of assumption that survives a migration undetected until real production data volume exposes it.
