Function App Won't Start After Disabling Storage Account Keys

AzureWebJobsStorage Managed Identity 8 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A previously healthy Function App stops entirely — not just individual triggers, the whole host fails to start, every trigger type included — right after a Storage Account used for AzureWebJobsStorage has shared key access disabled. Unlike the equivalent App Service scenario where only storage-dependent code paths break, here the app is completely down.

02Environment

  • Azure Functions on any plan (Consumption, Premium, Dedicated)
  • AzureWebJobsStorage configured as a traditional connection string containing AccountKey=
  • The referenced Storage Account recently had Shared Key Access disabled

03Diagnosis

This is a more severe version of the App Service storage-key scenario, because AzureWebJobsStorage isn't just something your application code calls — it's what the Functions host itself depends on for trigger management, checkpoints, and scale coordination. Confirm the cause quickly:

  • Check the timing of the outage against when Shared Key Access was disabled on the storage account referenced by AzureWebJobsStorage — a direct match confirms the cause without further digging.
  • Check platform-level startup logs (via Kudu or the portal's Log Stream) for an authentication failure specifically tied to the storage connection during host initialization, rather than any individual function's logs — the host fails before any function code runs.
Common misdiagnosis: because the failure is total and immediate, it's sometimes mistaken for a platform outage or a deployment issue. If it correlates with a storage account configuration change, it's almost certainly this — not an Azure platform problem.

04Root Cause

Every Function App (with limited exceptions in newer container-based deployment models) depends on Azure Storage at runtime for trigger coordination, checkpoints, and scale controller metadata — this is fundamentally different from App Service, which has no inherent storage dependency unless your application code adds one. When AzureWebJobsStorage is still configured with a legacy account-key connection string and that storage account disables Shared Key Access, the host itself can no longer authenticate to a resource it requires simply to start — so the entire app goes down, not just storage-dependent triggers.

05Fix

  • Enable a managed identity on the Function App if one isn't already present.
  • Grant the identity the required RBAC roles on the storage account — typically Storage Blob Data Owner, Storage Queue Data Contributor, and Storage Table Data Contributor, since the runtime uses blob, queue, and potentially table storage internally.
  • Migrate AzureWebJobsStorage to an identity-based connection rather than a connection string — this typically means replacing the single setting with a set of AzureWebJobsStorage__* settings (account name, credential type) that tell the runtime to authenticate via managed identity instead of a key. Check current Functions runtime documentation for the exact setting names for your runtime version, since this has evolved across versions.
  • Confirm the plan supports identity-based storage — Flex Consumption and Premium plans have the most complete support; verify your specific plan and runtime version before assuming full parity.
  • Test in a staging Function App pointed at a non-production storage account with the same Shared Key Access setting before applying this to production, given how completely the app goes down if the migration is incomplete.
Prevention tip: treat AzureWebJobsStorage migration as a required prerequisite — not an afterthought — any time a Storage Account backing a Function App is scheduled to have Shared Key Access disabled. Because the failure mode is total host failure rather than a degraded feature, this migration needs to happen before the storage change, not after.
