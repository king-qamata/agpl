Debugging JWT Validation Errors Behind Azure Front Door

OAuth / OIDC Azure Front Door 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

API requests with a valid bearer token return 401 Unauthorized when routed through Azure Front Door, but the exact same token succeeds when the client calls the origin (App Service, Container App, etc.) directly. Token validation logic hasn't changed — only the network path has.

02Environment

  • API secured with JWT bearer authentication, validating against an OAuth/OIDC provider (Azure AD or a custom identity provider)
  • Azure Front Door in front of the origin, often also handling TLS termination and WAF rules
  • Issue appears only through Front Door, not on direct origin calls

03Diagnosis

Since the token itself is valid against the origin, the difference has to be something Front Door changes about the request. Check these in order:

  • Authorization header stripped or rewritten. Confirm Front Door's rules engine (or any Rules Set) isn't stripping, renaming, or overwriting the Authorization header — this is the single most common cause.
  • Caching serving a stale or cross-user response. If caching is enabled on the route and the cache key doesn't vary by the Authorization header, Front Door may serve a cached 401 (or another user's cached response) instead of forwarding the request.
  • Audience (aud) claim mismatch. If Front Door's custom domain is what the client authenticates against, but the token's audience claim was issued for the origin's hostname, origin-side validation can reject it as intended for a different audience.
  • WAF rule false positive. A JWT's structure (base64 payload with special characters) can occasionally trip a WAF managed rule designed to catch injection attempts — check WAF logs for a block on the request before it even reaches the origin.
Common misdiagnosis: a 401 through Front Door but success direct-to-origin often gets treated as "Front Door is broken" and escalated as a platform issue. In the large majority of cases it's a specific, fixable configuration gap — caching, header handling, or audience mismatch — not a Front Door defect.

04Root Cause

Front Door sits between the client and the origin and can modify requests (via rules engine actions), cache responses, and apply WAF inspection — any of which can interfere with a bearer token that the origin would otherwise accept unmodified. Because direct-to-origin calls bypass all of this, they succeed while Front Door-routed calls fail, which is precisely why comparing the two paths is the fastest way to isolate the cause.

05Fix

  • Header stripping: review Front Door's rules engine configuration and ensure no rule modifies or removes the Authorization header on the affected route.
  • Caching: disable caching on authenticated API routes, or explicitly configure the cache key to vary by the Authorization header (or better, don't cache authenticated responses at all).
  • Audience mismatch: align the token's expected audience with whichever hostname is actually presented to the client — either issue tokens for Front Door's custom domain, or configure origin-side validation to accept that audience.
  • WAF false positives: check WAF logs for blocked requests; if a managed rule is triggering on legitimate JWTs, add a scoped exclusion for that rule on the specific header rather than disabling WAF broadly.
Prevention tip: when adding Front Door in front of an existing authenticated API, explicitly test the full auth flow through Front Door as part of the rollout — don't assume behavior that worked pre-Front Door carries over unchanged, since caching and rules engine behavior are opt-in but easy to enable by default in a starter configuration.
