Diagnosing Node.js Apps That Crash Under Load on App Service Linux

Node.js Event Loop 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A Node.js app responds normally under light traffic, but under moderate concurrent load it becomes unresponsive — requests hang or time out — without the CPU or memory metrics in the portal showing anything alarming. Restarting temporarily resolves it, and the pattern repeats once load returns.

02Environment

  • Node.js app on App Service Linux (or Container Apps), single process or with limited clustering
  • Handles concurrent requests, possibly with some synchronous computation, file I/O, or JSON parsing of large payloads in the request path

03Diagnosis

Node.js runs JavaScript on a single-threaded event loop — any synchronous, CPU-bound operation in a request handler blocks that thread for its entire duration, during which no other request can be processed, even though CPU utilization at the container level might look unremarkable if the blocking operation itself is short but frequent.

  • Check for synchronous operations in hot paths — synchronous file reads (fs.readFileSync), synchronous crypto operations, or large synchronous JSON parsing/stringification are common culprits.
  • Measure event loop lag directly rather than relying on CPU/memory graphs, which don't clearly show this pattern — Node's perf_hooks module or an APM tool can report event loop delay directly.
  • Check request payload sizes — a large JSON body parsed synchronously scales badly with both payload size and concurrent request count, and is easy to miss in testing with small payloads.
Node.js — quick event loop lag check
const { monitorEventLoopDelay } = require('perf_hooks');
const h = monitorEventLoopDelay();
h.enable();
setInterval(() => {
  console.log('event loop delay (ms):', h.mean / 1e6);
}, 5000);
Common misdiagnosis: because CPU and memory graphs often look normal, teams sometimes assume this is a network or downstream dependency issue. If the pattern is "fine under light load, unresponsive under concurrent load, no resource graph anomaly," event loop blocking should be the first thing checked, not the last.

04Root Cause

Any synchronous, blocking operation on Node's single event loop thread prevents all other in-flight requests from making progress for its duration — this includes CPU-bound JavaScript execution, synchronous I/O calls, and heavy synchronous parsing/serialization. Under light load, blocking operations are infrequent enough not to matter; under concurrent load, they queue up and requests start timing out even though the underlying resource utilization (CPU%, memory) doesn't necessarily spike in a way that's obvious in standard infrastructure metrics.

05Fix

  • Replace synchronous I/O with async equivalents — fs.readFile instead of fs.readFileSync, and equivalent async patterns for any other blocking I/O call in a request path.
  • Move genuinely CPU-bound work off the main thread — use worker threads (worker_threads) for heavy computation, so it doesn't block request handling for other concurrent users.
  • Stream large payloads instead of buffering and parsing synchronously where possible, particularly for large JSON bodies or file uploads.
  • Add event loop lag monitoring as a standing metric, not just a one-time diagnostic — this makes the pattern visible in normal monitoring rather than only during an active incident.
Prevention tip: load test with concurrency levels that match real production traffic, not just total request volume — event loop blocking specifically requires concurrent in-flight requests to manifest, so a sequential load test can miss it entirely even at high total throughput.
