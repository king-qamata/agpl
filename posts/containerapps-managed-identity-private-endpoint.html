Connecting Container Apps to Storage with Managed Identity and Private Endpoints

Zero Trust Managed Identity 8 min read

The Managed Identity plus Private Endpoint pattern covered elsewhere on this site for App Service and Functions applies just as directly to Container Apps — with a few ACA-specific wiring details. This walks through the full pattern for a Container App reaching a Storage Account with no account keys and no public network exposure.

Before you start
  • An existing Container Apps Environment, ideally with VNet integration already configured
  • A Storage Account with Shared Key Access and Public Network Access still enabled (you'll disable both here)

  1. Enable a managed identity on the Container App

    In the portal, go to your Container App → Identity, and enable a system-assigned identity (or attach a user-assigned one if you're sharing an identity across multiple apps).

  2. Grant RBAC on the Storage Account

    On the Storage Account, add a role assignment for the Container App's identity — typically Storage Blob Data Contributor for read/write, scoped to the account or a specific container.

    bash
    az role assignment create \
  --assignee <container-app-identity-principal-id> \
  --role "Storage Blob Data Contributor" \
  --scope /subscriptions/<sub>/resourceGroups/<rg>/providers/Microsoft.Storage/storageAccounts/<account>

  3. Create a Private Endpoint for the Storage Account

    Create a Private Endpoint targeting the Storage Account's blob (or relevant) sub-resource, placed in a subnet within the same VNet the Container Apps Environment is integrated with.

  4. Configure Private DNS

    Link a Private DNS Zone for privatelink.blob.core.windows.net (or the relevant service) to the VNet, so the Container App resolves the storage endpoint to its private IP rather than the public one. This is the step most often missed, and produces connectivity failures that look unrelated to DNS at first glance.

  5. Update application code to use identity-based auth

    Replace any connection-string-based storage client initialization with the identity-based equivalent — for example, using DefaultAzureCredential with the Azure SDK, which automatically picks up the Container App's managed identity when running in Azure.

  6. Disable public access and shared key auth

    Once the identity-based, private-network path is confirmed working, disable Allow storage account key access and set Public network access to Disabled on the Storage Account — same end state as the App Service and Functions posts on this site, now achieved for a Container App.

  7. Verify from inside the environment

    Confirm connectivity works from the Container App itself (not just from your local machine) — a shell into a running revision and a test request against the storage endpoint confirms the full path: identity, RBAC, private DNS, and network routing all working together.

Result: a Container App reaching Storage with no long-lived secrets and no public network exposure — the same end state as the App Service and Functions posts on this site, achieved through ACA's specific identity and networking configuration.
