Trimming Python Container Images with Multi-Stage Docker Builds

Intermediate Python 6 min read

A naive Python Dockerfile bakes compilers, build tools, and cached wheel files into the final image — none of which the running application needs. A multi-stage build separates what's needed to build dependencies from what's needed to run the app, often cutting image size substantially and speeding up cold starts tied to image pull time.

Before you start
  • An existing single-stage Python Dockerfile
  • Any dependencies with native extensions that require build tools (common culprits: cryptography, numpy, psycopg2)

  1. Identify the naive baseline

    A typical single-stage Dockerfile installs build tools, then dependencies, all in one image layer that ships to production carrying compiler toolchains it will never use again after the build step.

    Dockerfile — single-stage (before)
    FROM python:3.12
RUN apt-get update && apt-get install -y build-essential
COPY requirements.txt .
RUN pip install -r requirements.txt
COPY . .
CMD ["python", "app.py"]

  2. Split into a build stage

    Use a first stage specifically for installing dependencies, including any build tools needed for native extensions — this stage's size doesn't matter since it's discarded.

    Dockerfile — build stage
    FROM python:3.12 AS builder
RUN apt-get update && apt-get install -y build-essential
COPY requirements.txt .
RUN pip install --user -r requirements.txt

  3. Copy only the installed packages into a slim runtime stage

    The second stage starts from a slim base image and copies just the installed Python packages from the build stage — no compilers, no build-time cache.

    Dockerfile — runtime stage
    FROM python:3.12-slim
COPY --from=builder /root/.local /root/.local
COPY . .
ENV PATH=/root/.local/bin:$PATH
CMD ["python", "app.py"]

  4. Compare image sizes

    Build both versions and compare — the runtime-only image is typically meaningfully smaller, sometimes by several hundred megabytes depending on how many native-extension dependencies your app has.

    bash
    docker images | grep myapp

  5. Verify the app still runs correctly

    Native extensions compiled in the build stage need to be compatible with the runtime stage's base image — using the same base OS/Python version for both stages (just -slim vs full for the runtime) avoids the kind of glibc/library mismatch covered in the GLIBC troubleshooting post on this site.

  6. Consider further trimming with distroless or alpine bases

    For further size reduction, evaluate a distroless or Alpine-based runtime image — but test thoroughly, since Alpine's musl libc can reintroduce native-extension compatibility issues if any dependency wasn't built with musl compatibility in mind.

Result: a meaningfully smaller runtime image with faster pulls and cold starts, without changing anything about how the application actually runs — a straightforward, low-risk optimization for any Python container that isn't already using multi-stage builds.
