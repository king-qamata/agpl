Building a Durable Functions Orchestrator for Scheduled File Archival

Python Durable Functions 8 min read

Durable Functions lets you write multi-step, stateful workflows as ordinary-looking Python code, with the platform handling checkpointing and retry between steps. This walks through the orchestrator/activity/client pattern using a realistic example: a scheduled job that archives files older than a threshold via the Microsoft Graph API.

Before you start
  • Python Function App with the azure-functions-durable package
  • An Azure AD app registration if calling Microsoft Graph — see the MSAL configuration troubleshooting post on this site for the credentials this requires

  1. Understand the three function types

    Durable Functions splits work across three roles: a client function (typically timer or HTTP triggered) that starts the orchestration, an orchestrator function that defines the workflow steps in order, and one or more activity functions that do the actual work each step calls.

  2. Write the client function

    A timer trigger is a natural fit for a scheduled archival job — start the orchestration on a cron schedule rather than waiting for an HTTP call.

    Python — timer-triggered client
    import azure.functions as func
import azure.durable_functions as df

app = df.DFApp()

@app.timer_trigger(schedule="0 0 0 * * 0", arg_name="timer")  # weekly
@app.durable_client_input(client_name="client")
async def start_archival(timer: func.TimerRequest, client):
    await client.start_new("archival_orchestrator")

  3. Write the orchestrator function

    The orchestrator reads like sequential code but is actually replayed by the runtime for checkpointing — this is why orchestrator code must be deterministic (no direct API calls, no datetime.now(); use the provided context APIs instead).

    Python — orchestrator
    @app.orchestration_trigger(context_name="context")
def archival_orchestrator(context: df.DurableOrchestrationContext):
    files_to_archive = yield context.call_activity("list_old_files")
    results = []
    for file_id in files_to_archive:
        result = yield context.call_activity("archive_file", file_id)
        results.append(result)
    return results

  4. Write the activity functions

    Activities are ordinary functions — this is where actual API calls, database access, and non-deterministic work belongs, since activities aren't replayed the way orchestrators are.

    Python — activity
    @app.activity_trigger(input_name="fileId")
def archive_file(fileId: str) -> dict:
    # real Graph API call here, using credentials
    # validated per the MSAL config post on this site
    drive_service.move_to_archive(fileId)
    return {"file_id": fileId, "status": "archived"}

  5. Handle partial failures deliberately

    If one file fails to archive, decide explicitly whether the whole orchestration should fail or continue processing the rest — wrap individual call_activity calls in try/except within the orchestrator if partial success should be tolerated, rather than letting one failure abort the entire batch silently.

  6. Test locally with dummy credentials

    For any orchestration calling an external API like Graph, set up your test suite to mock the activity functions rather than hitting the real API — keeps tests fast and avoids needing live Azure AD credentials just to validate the orchestration logic itself.

Result: a scheduled, checkpointed workflow that survives individual step failures and restarts — the pattern that makes Durable Functions a better fit than a single long-running function for any multi-step batch job.
