Blob Trigger Taking Minutes to Fire: Switching to Event Grid-Based Triggering

Blob Trigger Event Grid 7 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A blob-triggered Function works correctly — it eventually processes every blob — but there's a noticeable, sometimes multi-minute delay between a blob landing in the container and the function actually firing. This is often first noticed under low-traffic conditions, where the delay is most visible, and can look like an intermittent or environment-specific problem.

02Environment

  • Azure Functions with a standard Blob Storage trigger (the default, polling-based version)
  • Consumption or Premium plan — the polling interval is a bigger factor at lower/idle scale
  • No errors in logs; the function simply runs later than expected

03Diagnosis

Confirm this is a triggering-latency issue and not a processing-latency issue first: check the timestamp of the blob's creation against the function's actual invocation start time in Application Insights. If there's a meaningful gap between the two — and the function itself runs quickly once it starts — the delay is happening before the function is even invoked, which points at the trigger mechanism itself rather than your code.

KQL — compare blob creation to function invocation time
requests
| where timestamp > ago(2h)
| where name == "YourBlobTriggerFunction"
| project timestamp, duration
| order by timestamp desc

Cross-reference against your storage account's own logs or activity for the actual blob creation timestamp. A gap of anywhere from under a minute up to several minutes is consistent with the default polling-based trigger, not a bug.

Common misdiagnosis: intermittent, unexplained delay is often chased as a cold start issue or an App Insights sampling artifact. If the function itself executes quickly once invoked, and the delay is specifically between blob creation and invocation, that's the trigger's own polling behavior — a different problem from cold starts, and not fixed by any of the cold start mitigations covered elsewhere on this site.

04Root Cause

The original Blob Storage trigger design polls the container for changes rather than reacting to them immediately — it periodically scans for new or modified blobs. This polling interval is what introduces latency between a blob actually appearing and the function noticing it, and that latency is inherent to how the polling trigger works, not something tunable away to zero.

05Fix

Newer versions of the Storage extension (5.x and later) support an Event Grid-based Blob trigger instead — the container is subscribed to via an Event Grid event subscription, and the function is invoked as a direct reaction to the blob-created event rather than being discovered on the next poll cycle. This removes the polling delay essentially entirely.

  • Upgrade to Storage extension 5.x+ (via the appropriate NuGet/npm/pip package or extension bundle version) if not already on it.
  • Change the trigger's source to EventGrid in the binding definition, instead of the default polling source.
  • Create an Event Grid event subscription on the storage account, targeting the function's blob extension webhook endpoint, filtered to the relevant container and blob-created events.
  • Note the Flex Consumption plan requirement: if you're on Flex Consumption specifically, this isn't optional — that plan only supports the Event Grid-based trigger, not the legacy polling version, so this migration may be required rather than just an optimization.

Full setup steps are in the Event Grid-based blob trigger tutorial on this site.

Prevention tip: for any new blob-triggered function where latency matters, default to the Event Grid-based source from the start rather than the polling version — there's little reason to accept polling latency now that the event-based option is broadly available.
