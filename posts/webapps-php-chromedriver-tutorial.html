Running Headless Chrome Automation in PHP on App Service Linux

PHP Custom Containers 8 min read

Browser automation (scraping, PDF generation, visual testing) needs a real browser process, which App Service's standard PHP image doesn't include. This walks through a custom container setup running Chrome headlessly via ChromeDriver, with the specific architecture decision that determines whether it scales cleanly: on-demand driver instances instead of one shared, persistent service.

Before you start
  • A custom Docker image for PHP on App Service Linux
  • The Facebook/php-webdriver package via Composer

  1. Install Chrome, ChromeDriver, and Xvfb in the image

    Chrome needs a display to render into even in headless mode in some configurations, and matching Chrome/ChromeDriver versions matters — a mismatch is a common source of driver startup failures. Xvfb provides a virtual framebuffer display so nothing needs real GPU/display hardware.

  2. Start Xvfb as a background service

    Run Xvfb once per container, supervised so it restarts if it dies, rather than starting it per-script — this is a genuinely shared, safe-to-share resource unlike the ChromeDriver process itself.

    supervisord.conf — Xvfb entry
    [program:xvfb]
command=Xvfb :99 -screen 0 1920x1080x24
autorestart=true
stdout_logfile=/home/LogFiles/xvfb.log

  3. Choose on-demand ChromeDriver instances, not a shared service

    A single persistent ChromeDriver process listening on one fixed port (e.g. 9515) works fine for one script at a time, but under any concurrency it becomes a source of port conflicts and shared-state bugs between unrelated requests. Starting a fresh ChromeDriver instance per script, on a random port, avoids this entirely at the cost of slightly higher per-request startup time.

    PHP — start an isolated instance per script
    putenv('HOME=/tmp/www-data');
putenv('DISPLAY=:99');

$options = new ChromeOptions();
$options->addArguments([
    '--headless=new',
    '--no-sandbox',
    '--disable-dev-shm-usage',
    '--user-data-dir=' . '/tmp/chrome-profiles/profile-' . uniqid(),
]);

$capabilities = DesiredCapabilities::chrome();
$capabilities->setCapability(ChromeOptions::CAPABILITY, $options);

$driver = ChromeDriver::start($capabilities);

  4. Always clean up, even on failure

    An orphaned Chrome or ChromeDriver process from a script that errored out before calling quit() leaks memory and eventually exhausts container resources. Wrap driver usage in try/finally so cleanup happens regardless of outcome.

    PHP
    try {
    $driver = ChromeDriver::start($capabilities);
    $driver->get('https://example.com');
    // ... work ...
} finally {
    if (isset($driver)) {
        $driver->quit();
    }
}

  5. Set realistic memory expectations

    Each Chrome instance uses roughly 300–500MB. Size the App Service plan's memory with real headroom for however many concurrent automation scripts you expect, and set memory_limit in php-azure.ini accordingly rather than leaving PHP's default.

  6. Add a health check endpoint

    A simple endpoint that checks Chrome, ChromeDriver, and Xvfb are all present and Xvfb is running gives you a fast way to confirm the container's automation stack is healthy, separate from your application's own health.

Result: isolated, concurrency-safe Chrome automation in PHP, with the shared Xvfb display as the only genuinely shared resource — everything else scoped per-script and cleaned up explicitly.
