"GLIBC Version Not Found": Diagnosing Base Image Mismatches

Base Images Alpine vs Debian 6 min read

02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A container fails to start, and the logs show an error along the lines of version 'GLIBC_2.XX' not found or Error loading shared library ... No such file or directory. The image built and pushed successfully — it only fails at container startup, sometimes only after switching or updating a base image tag.

02Environment

  • Azure Container Apps or Web App for Containers running a custom image
  • Base image recently changed — commonly a move to or from an Alpine-based image
  • Application includes a precompiled binary or native dependency (a compiled language runtime, or a native Node/Python extension)

03Diagnosis

This error is almost always a signal that the binary was compiled against glibc (the GNU C Library used by Debian, Ubuntu, and most mainstream Linux distributions), but is now running inside a container based on Alpine Linux, which uses musl libc instead — a different, smaller C library that isn't binary-compatible with glibc.

  • Check your Dockerfile's FROM line — did it change from a Debian/Ubuntu-based tag to an Alpine one (or vice versa) recently?
  • Run ldd --version inside the container (or a matching local container) to confirm which C library and version is present.
  • Identify which binary is throwing the error — it's frequently a native dependency pulled in transitively by a package manager, not code you wrote directly.
Common misdiagnosis: teams sometimes assume this is a corrupted build or a registry caching issue and try rebuilding or re-pushing the same image repeatedly. The image is fine — it's simply built for a different C library than the one present at runtime.

04Root Cause

Alpine's use of musl instead of glibc is a deliberate design choice that makes Alpine images very small, but it means any binary compiled expecting glibc symbols will fail to load on Alpine, and vice versa. This commonly surfaces after switching base images for size optimization, or after a base image maintainer changes the underlying distribution in a new tag without an obvious naming signal.

05Fix

  • Match the base image to your binaries: if your dependencies are compiled against glibc, stay on a Debian/Ubuntu-based image rather than switching to Alpine purely for size.
  • Rebuild for musl: if you specifically want Alpine's smaller footprint, rebuild native dependencies against musl (many ecosystems, like Node's node:alpine tags, publish musl-compatible builds — but third-party native modules may not).
  • Use a glibc compatibility layer as a last resort: Alpine has a community gcompat package that provides partial glibc compatibility, but treat this as a stopgap, not a long-term fix — it doesn't cover every case.
  • Pin base image tags explicitly: avoid loosely-versioned tags that could silently swap the underlying distribution out from under you between builds.
Prevention tip: when evaluating a switch to Alpine for image size, test the full dependency tree in a local Alpine container before deploying — don't assume compatibility just because the build succeeds. Build success and runtime compatibility are separate questions for compiled dependencies.
