Blob Trigger and Bindings Walkthrough, Start to Finish

Beginner Blob Storage 7 min read

Blob-triggered Functions are one of the most common serverless patterns — process a file the moment it lands in storage. This builds one from scratch: trigger, input binding, and output binding, with the exact configuration details that the missing bindings post on this site assumes you already have working.

Before you start
  • Azure Functions Core Tools and the Azure CLI installed
  • An existing Storage Account, or willingness to create one during this walkthrough

  1. Scaffold the function with a Blob trigger

    bash
    func init BlobDemo --worker-runtime dotnet
cd BlobDemo
func new --name ProcessUpload --template "Azure Blob Storage trigger"

  2. Set the connection in local.settings.json

    Point AzureWebJobsStorage (or a dedicated connection setting) at your storage account's connection string locally, so triggers resolve correctly before you ever deploy.

    local.settings.json
    {
  "IsEncrypted": false,
  "Values": {
    "AzureWebJobsStorage": "<your-connection-string>",
    "FUNCTIONS_WORKER_RUNTIME": "dotnet"
  }
}

  3. Confirm the trigger path in function.json

    The path value determines which container (and optional blob name pattern) fires the function — this is exactly the field that causes silent failures when it doesn't match the real container name.

    function.json (generated) — key fields
    {
  "bindings": [
    {
      "name": "myBlob",
      "type": "blobTrigger",
      "direction": "in",
      "path": "uploads/{name}",
      "connection": "AzureWebJobsStorage"
    }
  ]
}

  4. Add an output binding

    Add a second binding to write a result — for example, a processed copy to a different container. Output bindings let you avoid writing storage SDK boilerplate for the common case.

    function.json — add an output binding
    {
  "name": "outputBlob",
  "type": "blob",
  "direction": "out",
  "path": "processed/{name}",
  "connection": "AzureWebJobsStorage"
}

  5. Test locally with a real upload

    Run func start, then upload a test file to the uploads container using Azure Storage Explorer or the CLI, and confirm the function fires and a processed file appears in the processed container.

    bash
    az storage blob upload --account-name mystorageacct --container-name uploads --file test.txt --name test.txt

  6. Deploy and verify against the real trigger

    Publish with func azure functionapp publish, then repeat the upload test against production. If the function doesn't fire, the missing bindings troubleshooting post covers exactly this failure mode and how to isolate it.

Result: a working Blob trigger with both input and output bindings, and a clear picture of which fields (connection name, path) are the ones that actually matter when something doesn't fire as expected.
