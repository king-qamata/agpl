Diagnosing Cold Start Failures in Consumption Plan Functions

Consumption Plan Application Insights 8 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

An HTTP-triggered function on a Consumption plan responds in under 100ms most of the time, but a subset of requests — usually the first request after a period of inactivity — takes 3 to 8 seconds or times out entirely at the client. Customers report this as "intermittent slowness" or "random timeouts," which makes it easy to misdiagnose as a downstream dependency issue rather than a hosting-model behavior.

02Environment

  • Function App hosted on Consumption Plan (Y1 SKU)
  • Runtime: .NET or Node.js in-process, HTTP trigger
  • Client is a synchronous frontend or API gateway with a fixed timeout (often 3–5 seconds)
  • Traffic pattern: bursty, with idle gaps longer than ~20 minutes

03Diagnosis

Start in Application Insights rather than guessing. The Performance blade will show a bimodal latency distribution — a tight cluster near the true execution time, and a second cluster far to the right. That second cluster is your cold start population.

Kusto Query Language (KQL) — isolate cold start requests
requests
| where timestamp > ago(24h)
| where name == "GET /api/YourFunction"
| extend isColdStart = iff(duration > 3000, "cold", "warm")
| summarize count(), avg(duration) by isColdStart, bin(timestamp, 1h)
| order by timestamp desc

Cross-reference against the Live Metrics stream during a known idle-then-burst window. If you see a spike in "Instances" at the same moment latency spikes, that confirms the platform is spinning up a new worker rather than reusing a warm one.

Common misdiagnosis: engineers often chase this as a database connection issue because the trace shows a slow SQL call first in the request. In reality, the SQL client's connection pool is also cold — the entire process, not just the function, is starting fresh.

04Root Cause

On the Consumption plan, Azure deallocates idle instances and scales to zero. The next incoming request triggers a new instance: the Functions host boots, the language worker starts, and — critically — any static initializers, dependency injection container setup, or connection pools in your code run for the first time. This is the cold start. It is expected platform behavior, not a bug, but it becomes a customer-facing problem when a caller's timeout is shorter than the cold start duration.

05Fix

There is no single fix — match the option to the constraint:

  • If the timeout budget is fixed and short: move to a Premium plan with pre-warmed instances (minimumElasticInstanceCount). This is the only option that structurally removes cold starts rather than reducing their frequency.
  • If cost rules out Premium: reduce cold start duration itself — trim package dependencies, avoid heavy static constructors, and lazy-load anything not needed on the first request path.
  • If traffic is predictable: a scheduled "warm-up" timer trigger pinging the function every few minutes keeps an instance alive, though this does not survive scale-out to a second instance under burst load.
  • Always: increase the caller's timeout where possible, or return an immediate 202-style response for long-running work instead of blocking the caller on a cold path.
Prevention tip: add an Application Insights availability test or alert on the requests | duration p95 metric, not just average duration — averages hide cold starts in high-volume apps, but p95/p99 exposes them immediately.
