Static Web App API Calls Failing with 401: Diagnosing Managed Function Auth

Managed Functions Auth 6 min read
01SYMPTOM
02ENVIRONMENT
03DIAGNOSIS
04ROOT CAUSE
05FIX

01Symptom

A user is clearly logged in — the SWA frontend shows their profile, /.auth/me returns a valid identity — but calls to /api/* return 401 Unauthorized anyway. This is specific to the managed Functions integration covered in the managed vs bring-your-own API guide on this site.

02Environment

  • Static Web App using managed Functions (linked API, not bring-your-own)
  • Custom auth provider or built-in Entra auth configured, as covered in the AAD B2C tutorial on this site
  • Some API routes work fine for logged-in users; others 401 specifically

03Diagnosis

Two separate authorization layers are involved, and a mismatch between them is the usual cause:

  • staticwebapp.config.json route rules — check whether the specific failing route has a allowedRoles restriction that the logged-in user's role doesn't satisfy. A user can be authenticated without holding the specific role a route requires.
  • The function's own authorization level — confirm the function isn't set to a level (like function or admin) that expects a function key, which conflicts with how SWA proxies authenticated requests. Managed Functions behind SWA generally expect anonymous authorization level at the function itself, with SWA's own routing rules handling access control instead.
staticwebapp.config.json — role-restricted route
{
  "routes": [
    {
      "route": "/api/admin/*",
      "allowedRoles": ["administrator"]
    }
  ]
}
Common misdiagnosis: because the user is clearly authenticated at the frontend, the 401 is sometimes chased as a frontend token-passing bug. If /.auth/me confirms the identity is valid, the issue is in how SWA's route rules or the function's own auth level gate that specific endpoint, not in whether the user is logged in at all.

04Root Cause

SWA's managed Functions integration handles authentication (confirming who the user is) automatically, but authorization (what that user is allowed to call) is controlled separately via staticwebapp.config.json route rules and roles. A route restricted to a role the current user doesn't have returns 401/403 regardless of how solid their authentication is — and a function set to a non-anonymous authorization level can conflict with SWA's own proxying, producing the same symptom from a different cause.

05Fix

  • Set function authorization level to anonymous for functions served through the managed API integration, letting staticwebapp.config.json route rules be the actual access control layer instead.
  • Audit allowedRoles on each route against the roles your auth provider actually assigns — confirm the role name matches exactly, including case, between the config file and what the identity provider issues.
  • Check role assignment for the specific user hitting the failing route — via the Static Web Apps role management UI or your custom auth provider's role claims, depending on setup.
  • Test with /.auth/me directly to see exactly what roles the platform believes the current user has, comparing that against what the failing route requires.
Prevention tip: keep a single source of truth for role names (a constants file, or documented list) referenced by both your identity provider configuration and staticwebapp.config.json — role name typos between the two are the single most common cause of this exact symptom.
