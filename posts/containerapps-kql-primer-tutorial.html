Reading ACA Logs in Log Analytics: a KQL Primer

Beginner Log Analytics 6 min read

Container Apps logs don't live in one obvious place the way Kudu centralizes Web Apps logs. This covers the specific tables you need, which is a prerequisite for every Container Apps troubleshooting post on this site.

Before you start
  • A Container Apps Environment with Log Analytics workspace integration enabled (on by default for most environments)
  • Access to the Log Analytics workspace linked to the environment

  1. Find the right workspace

    Container Apps logs go to the Log Analytics workspace configured on the Container Apps Environment, not the individual app — check the environment's overview page for which workspace is linked, then open Logs from there.

  2. Query console output (stdout/stderr)

    Application-level logs — anything your container writes to stdout or stderr — land in ContainerAppConsoleLogs_CL.

    KQL
    ContainerAppConsoleLogs_CL
| where TimeGenerated > ago(1h)
| where ContainerAppName_s == "my-container-app"
| project TimeGenerated, ContainerName_s, Log_s
| order by TimeGenerated desc

  3. Filter to a specific container in a multi-container revision

    If Dapr is enabled, this is exactly where you'd isolate the sidecar's own logs — filter ContainerName_s to daprd instead of your app's container name, as covered in the Dapr sidecar checklist on this site.

    KQL
    ContainerAppConsoleLogs_CL
| where ContainerAppName_s == "my-container-app"
| where ContainerName_s == "daprd"
| order by TimeGenerated desc

  4. Query system-level events

    Platform-level events — revision provisioning, scaling decisions, health probe failures — land in ContainerAppSystemLogs_CL, separate from your application's own console output.

    KQL
    ContainerAppSystemLogs_CL
| where TimeGenerated > ago(6h)
| where ContainerAppName_s == "my-container-app"
| project TimeGenerated, Log_s, Reason_s, Type_s
| order by TimeGenerated desc

  5. Correlate scaling events with traffic

    Combine system logs with request volume to confirm scaling actually happened when you expected it to — useful when validating a fix to the kind of issue covered in the Envoy scaling troubleshooting post.

    KQL
    ContainerAppSystemLogs_CL
| where ContainerAppName_s == "my-container-app"
| where Reason_s has "Scal"
| project TimeGenerated, Log_s, Reason_s
| order by TimeGenerated desc

  6. Pin your most-used queries

    As with any Log Analytics workflow, pin the queries you'll rerun during every incident — a filtered console log view and a system events view cover the majority of first-response triage for Container Apps.

Result: working queries against both ContainerAppConsoleLogs_CL and ContainerAppSystemLogs_CL — the two tables every other Container Apps troubleshooting post on this site assumes you can already query.
