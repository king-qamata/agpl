.NET on App Service: Capturing a dotnet-trace for High CPU and Slow Requests

Intermediate .NET Core 7 min read

The Kudu Process Explorer approach covered in this site's App Service high CPU post works for any language, but .NET has a more precise tool available: dotnet-trace, which reads from the runtime's own EventPipe. This walks through capturing a trace directly against a running App Service instance or custom container.

Before you start
  • A .NET Core / .NET 5+ application on App Service Linux (built-in image or custom container)
  • SSH access via the Kudu console

  1. SSH into the container

    From https://<your-app>.scm.azurewebsites.net, open the SSH console (or Bash/CMD debug console for built-in images).

  2. Confirm curl is available

    On Ubuntu/Debian-based images, install curl if missing; Alpine-based images use a different package manager.

    bash — Debian/Ubuntu base
    apt-get update && apt-get install -y curl
    bash — Alpine base
    apk add curl

  3. Download and install dotnet-trace

    bash
    curl -L https://aka.ms/dotnet-trace/linux-x64 -o dotnet-trace
chmod +x dotnet-trace

  4. Find the running process ID

    bash
    ./dotnet-trace ps

  5. Start the trace and reproduce the issue

    Start collection against the PID, then actively reproduce the slow behavior (send the requests that trigger it) while the trace is running — a trace with no load captured tells you nothing.

    bash
    ./dotnet-trace collect -p <PID>
# reproduce the issue now, then:
# press Enter or Ctrl+C to stop collection

  6. Download and analyze the trace file

    This generates a .nettrace file in the working directory. Download it via the Kudu VFS API and open it with a compatible viewer such as PerfView or the Visual Studio profiler to identify which method is consuming CPU time.

    URL pattern
    https://<your-app>.scm.azurewebsites.net/vfs/<path-to-file>

  7. For unhandled exceptions without a visible stack trace

    If the app shows a generic error page instead of exception details, check the docker logs (enable from the portal if not already), or temporarily set ASPNETCORE_ENVIRONMENT=Development to surface full stack traces — but revert this immediately after diagnosis, since verbose error output isn't appropriate for production.

Result: a captured .NET runtime trace with real profiling data — method-level CPU attribution rather than the process-level view Kudu's Process Explorer alone provides.
