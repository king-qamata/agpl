ACI vs Web App for Containers vs ACA: Choosing the Right Azure Compute Service

Architecture Decision Guide 8 min read

All three services run containers, but they solve different problems. This is the decision guide worth having before picking one — getting it wrong usually doesn't show up until you need a feature the chosen service doesn't have.

01What each one actually is

Azure Container Instances (ACI) is the closest thing Azure has to docker run in the cloud — no orchestration layer, no App Service Plan, just a container given CPU and memory and started immediately. It's built for short-lived and batch workloads, not always-on services.

Web App for Containers is Azure App Service running your container instead of your code directly. You get everything App Service normally provides — deployment slots, managed TLS, custom domains, built-in authentication — with a container as the deployment artifact.

Azure Container Apps (ACA) is Microsoft's serverless platform for cloud-native workloads, built on managed Kubernetes underneath (KEDA for event-driven scaling, Envoy for ingress, optional Dapr integration) without exposing cluster management to you directly.

03Decision guide

A few scenarios where the choice is usually clear-cut:

  • One-off batch processing or scheduled scripts → ACI. No need for a continuously running service, billed only for actual runtime.
  • A traditional website (WordPress, Django, ASP.NET, Laravel) → Web App for Containers. Deployment slots and built-in auth are hard to beat for this shape of workload — and this site's own WordPress CORS post and container crash post both cover Web App for Containers specifically for this reason.
  • A microservices architecture with independent scaling per service → ACA. Revisions and traffic splitting exist specifically for this.
  • Event-driven processing (Service Bus, Event Hubs, Kafka, Queue Storage) → ACA. Native KEDA-based autoscaling from event sources is the reason this exists.
  • Cost-sensitive workloads with long idle periods → ACA. Scale-to-zero means you're not paying for idle compute the way you would on Web App for Containers or a minimum-replica ACA config.
  • Enterprise line-of-business web application → Web App for Containers. The maturity of App Service's operational tooling and enterprise integrations usually outweighs ACA's cloud-native features for this shape of app.
The practical test: if you're reaching for deployment slots and built-in auth, you want Web App for Containers. If you're reaching for scale-to-zero and event-driven triggers, you want ACA. If you just need a container to run once and exit, you want ACI — resist the temptation to over-engineer a batch job onto a platform built for always-on services.
