Automating Image Resizing on Blob Upload with Event Grid and Functions

Intermediate Event Grid · Blob Storage 7 min read

Thumbnail generation is one of the most common practical uses of an event-driven Function, and it's a good showcase for the Event Grid-based Blob trigger covered in the Event Grid blob trigger tutorial on this site — near-instant reaction matters here, since users expect a thumbnail to exist almost immediately after upload.

Before you start
  • A general-purpose v2 Storage Account with two containers: one for original uploads, one for resized output
  • The Event Grid-based blob trigger already configured (see the linked tutorial above)

  1. Set up the Event Grid-triggered function

    Follow the Event Grid blob trigger tutorial to subscribe your function to Blob Created events on the uploads container, filtered to image file extensions.

    Example filter
    Subject Ends With: .jpg
Subject Ends With: .png

  2. Read the uploaded blob via input binding

    Bind the triggering blob as an input stream, using the event payload's blob URL to resolve the binding path dynamically.

    function.json — input binding on the same path
    {
  "name": "inputBlob",
  "type": "blob",
  "direction": "in",
  "path": "uploads/{data.url}",
  "connection": "AzureWebJobsStorage"
}

  3. Resize the image in the function body

    Use an image processing library appropriate to your language (for example, ImageSharp for .NET, Pillow for Python, or sharp for Node.js) to generate one or more resized versions — commonly a thumbnail and a medium size.

  4. Write the resized output via output binding

    Write each resized version to the output container using a blob output binding, keeping a predictable naming convention (e.g. appending -thumb) so consuming applications know where to find each size.

    function.json — output binding
    {
  "name": "outputBlob",
  "type": "blob",
  "direction": "out",
  "path": "resized/{data.url}-thumb",
  "connection": "AzureWebJobsStorage"
}

  5. Handle non-image uploads gracefully

    Even with extension filtering on the Event Grid subscription, validate the actual file content in the function before processing — a mismatched extension or corrupted upload should fail cleanly rather than throwing an unhandled exception that shows up as a failed invocation in your monitoring.

  6. Verify end to end and check latency

    Upload a test image and confirm the resized version appears within seconds — use the Application Insights KQL tutorial on this site to compare upload timestamp against function invocation time, the same pattern used to diagnose the polling-based trigger's latency in the first place.

Result: images resized automatically and near-instantly on upload, using the Event Grid-based trigger rather than the polling-based default — the practical payoff of the latency fix covered elsewhere on this site.
